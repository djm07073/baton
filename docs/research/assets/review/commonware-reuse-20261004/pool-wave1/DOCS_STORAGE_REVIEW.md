# Updated central storage documentation review

Reviewed the current working-tree versions of `docs/execution/README.md`, `interfaces.md`, `qmdb.md`, `docs/overview/rust-interfaces.md`, and `docs/reference/integration.md` on 2026-10-04. This review treats the latest Executor/Storage split as authoritative. It reviews documentation and source boundaries; it does not establish a compiled dependency graph, executable adapter, storage proof, or protocol implementation. Only this review file was written.

## Verdict

The central prose now describes a credible maximum-reuse development path: reuse concrete QMDB batches and database lifecycle beneath a thin proposed Storage boundary; retain transaction computation, execution-tree selection, certification and normal-path peer synchronization in Executor. It does not require the full Stateful Application/actor. Preparation computes the selected commitment before full-result signing. It clearly distinguishes existing sealed-parent forks from additional rootless effects/read overlays.

Two small source-backed corrections remain. The Alto storage analogy is incorrect; the release recipe should state the prior-barrier observation requirement explicitly. Both were sent to the root reviewer. Upcoming diagram/E2E/overview synchronization is coherence work rather than evidence that these corrected central contracts remain wrong.

## Concrete corrections

### 1. Remove Alto from the staged-computation/sealed-storage analogy

At the inspected `docs/execution/qmdb.md:104`, the sentence “Alto similarly places compute/prepare inside its application and sealed lifecycle” is unsupported by the cited chain application. At the pinned Alto revision, `Application::Input = ()`; propose obtains ancestry, derives timestamp, generates random opaque load bytes, and constructs a block. Verify checks ancestry, size and timestamp. There is no QMDB transaction computation, storage preparation, or sealed-batch lifecycle in that application. [Alto application, lines 53–144](https://github.com/commonwarexyz/alto/blob/1d87569348b5560699465a72d691d90f18affb9c/chain/src/application.rs#L53).

Keep Alto as a consensus/body/handle-composition reference in integration.md. Use Constantinople for the staged computation followed by state/history Merkleization example. Its execution module explicitly stages account state, computes final account values/history updates, and returns merkleized commitments; `compute` returns a staged batch and updates rather than a newly rooted result. Its fixed account/transfer semantics and consensus block boundary are examples, not adopted Baton semantics. [Constantinople execution, lines 1–85 and 154 onward](https://github.com/commonwarexyz/constantinople/blob/3b6c92e76bf582855615844a4175b8304808f6a9/crates/application/src/consensus/execution.rs#L1).

### 2. State the release barrier sequencing obligation

At the inspected `docs/execution/qmdb.md:88`, the release recipe correctly permits later apply while an already-returned barrier remains pending and prohibits overlapping mutation method bodies. Add that the previous barrier must be observed before finalizing again. The release `DatabaseSet::finalize` contract states this separately; sequential method bodies alone do not satisfy it. The dirty suffix created by later apply also needs subsequent covering finalization. [Release DatabaseSet, lines 510–601](https://github.com/commonwarexyz/monorepo/blob/v2026.9.0/glue/src/stateful/db/mod.rs#L510).

This is a narrow missing API obligation, not a reason to collapse native and release recipes or introduce a new storage algorithm.

## Proposed-interface assembly detail to settle later

The traits are proposed seams, not source APIs. `Storage::prepare` consumes completed material and returns `PreparedResult`; both `Executor::sign_result` and `Storage::apply` take a prepared result by value. A concrete implementation can retain/clone prepared material internally, so this is not a claim that the declarations cannot compile. However, the eventual concrete adapter should show how signing and applying share one prepared binding without recomputing or losing material. Upstream `DatabaseSet::Merkleized` already has `Clone + Send + Sync`, explicitly preserving the same sealed branch cheaply. Prefer retaining or cloning that existing material rather than inventing a duplicate batch abstraction. [Native associated sealed type](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/glue/src/stateful/db/mod.rs#L512).

Likewise, the current generic Storage facade supplies no transaction execution-view method. This is compatible with the prose stating concrete QMDB access stays inside the implementation and with unresolved rootless adapter choices. Do not claim these declarations alone provide a ready-to-use generic Executor→Storage branch-access assembly. The concrete adapter must connect the associated types and selected valid view. This is remaining implementation detail, not a request to add another public trait now.
