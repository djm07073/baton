## Existing APIs do not erase these specific gaps

The source supports concrete handles without the abandoned framework, but it does not supply all application semantics:

- `glue::stateful::Application` is a real higher-level lifecycle with application block/context/provider types and merkleized proposal results (`glue/src/stateful/mod.rs:154-213`). Its Provider may supply transactions; that is not a complete pool, nor a reason to force every speculative attempt through this lifecycle. The current App can reuse its DB utilities independently.
- `Unmerkleized` supplies consuming merkleization; concrete wrappers supply reads/writes. `Merkleized` supplies root and sealed-parent child creation (`db/mod.rs:296-324`). `DatabaseSet::new_batches` starts at applied DB state and `fork_batches` starts at a pending merkleized parent (`541-550`). There is no generic unsealed-parent fork or arbitrary historical snapshot getter hidden in those contracts. The rootless integration gap must remain stated.
- `DatabaseSet` requires non-overlapping mutation methods (`493-497`), separates apply from finalize/durability (`559-568`) and can reopen specified targets (`527-536`). These are sufficient mechanisms for one App mutation owner, not a ready-made transaction/output/provenance cross-store commit. The exact App recovery linkage cannot be editorially removed.
- A future pool tracks submitted futures and exposes completion (`utils/src/futures.rs:20-58`); `push` does not enforce a capacity budget. Existing runtime placement and App resource accounting remain necessary. They do not need a new public executor layer.
- Generic certificate APIs authenticate bytes according to their configured scheme; QMDB sync authenticates material against a caller-trusted target. Full execution context, compatible App f+1 signing and target authorization remain App decisions (round16 source evidence). One App handler can perform those checks directly.

## Distinctions that should remain even in a smaller document

**Pool candidates versus body custody.** The pool handles proposal eligibility and transaction lifecycle. Marshal durably retains complete blocks, including foreign transactions never locally admitted. Merging those stores conceptually would make foreign/canonical validity depend on local selection and break cancellation/retention reasoning.

**Candidate metadata versus execution attempt.** Repeated verify can refresh one block's facts without launching it twice. That block executed after different merged prefixes is different work. Exact candidate and current-attempt identities are necessary; their representation can remain ordinary App state instead of separate components.

**App applied identity versus Marshal cursor.** App must recover the state/output/provenance associated with an input; Marshal separately persists acknowledged delivery. This is not duplicate cursor machinery that can be deleted. The App need not recreate Marshal delivery indexing, but it must recognize exact already-applied redelivery.

**Imported candidate storage versus canonical writer.** A candidate sync may prepare a separate DB without owning canonical adoption. Its isolated storage operations do not imply a second canonical writer. Same-store import must acquire the existing exclusive authority before mutation; direct/import adoption converges at the one writer.

**Logical retirement versus physical retention.** Scheduler removal of a conflicting branch does not prove workers stopped or material is no longer required by queries/recovery/serving. Existing Arc/DB/Archive handles and explicit retention obligations can carry this distinction; a new retention service is not mandated.

**Native body/history proofs versus result material.** Marshal's block/history custody and QMDB operation proofs do not retain arbitrary application outputs or authenticate runtime execution by themselves. An App result/material retention policy is necessary, but it can reuse existing storage/transport mechanisms instead of becoming a second generic proof archive.

## Concrete simplification recommendation

`docs/execution/interfaces.md:5-14` repeated a four-row callback overview plus future/receiver, synchronous Reporter and typed-handle prose. Those contracts already have their canonical implementation explanation in `docs/baton/interfaces.md` and actual signatures in `docs/overview/rust-interfaces.md`; the entry guide also summarizes them. This is a parallel callback specification inside the execution page, not an additional execution responsibility.

Root approved replacing that block with one direct callback-contract/reference sentence. Applied the narrow consolidation while retaining the `Interface overview` heading/anchor and every exact execution identity, attempt ownership, readiness, completion/apply and result-certification paragraph. This is useful consolidation, unlike merely deleting occurrences of “trait” or shortening an adopted failure requirement.

No mandatory overlay/read-view service, second result relay/archive, scheduler writer or importer writer remained to remove. The pages already explicitly make those responsibilities concrete/internal or optional. Further deletion of the distinction paragraphs above would hide required semantics instead of simplifying implementation. Core tables can remain navigation summaries; the canonical callback pseudocode should remain only at its current owner.
