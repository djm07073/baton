## Confirmed clarification and minimal fix

The last paragraph of `docs/execution/interfaces.md` formerly called `n-f` “the native N5f1 quorum” and allowed a compatible quorum adapter. That wording was too broad for the actual Multimmit key roles and could suggest that changing a count makes its threshold shares usable for App `f+1` signing.

- `utils/src/faults.rs:53-66` defines the generic `Faults::quorum` as `n-max_faults(n)`. For N5f1 and `n=5f+1`, this is `4f+1`.
- Actual Multimmit uses ordinary BLS signatures for blocks/votes and V/L-QC aggregation, a separate `n-2f` DA sharing and a separate `2f+1` nullification sharing (`consensus/src/multimmit/scheme/bls12381_threshold/mod.rs:1-14`). Construction enforces those sharing thresholds (`503-505`). None is a preexisting App execution-result subject or `f+1` role.
- Generic BLS threshold signer/verifier construction checks `polynomial.required() == participants.quorum::<M>()` (`cryptography/src/bls12381/certificate/threshold/mod.rs:109-124,157-171`). Recovery uses that polynomial, while certificate verification checks the recovered group signature (`350-414`). A different external counter does not change the existing sharing's algebraic threshold.
- Independent-signature certificate packaging also has quorum behavior: Ed25519 assembly requires the configured scheme quorum and verification checks it again (`cryptography/src/ed25519/certificate/mod.rs:183-206,229-241`). Reusing a primitive is not evidence that its default acceptance threshold is App `f+1`.

Changed only that paragraph to name `N5f1::quorum(n)` precisely, distinguish native key roles, require compatible certificate/key material and quorum handling, and explicitly say that an adapter cannot lower an existing BLS polynomial threshold. Added direct links to the existing native and generic threshold source. The result keys, codec, signing range and primitive selection remain open; no new native quorum, signer service or format was adopted.

## Adversarial analytical traces

**Native sharing reused with a lower counter.** For `n=6,f=1`, App wants two result authorizations. Native DA and nullification sharings retain their own four- and three-share thresholds; an external `count >= 2` check does not recover either sharing from two shares or create an execution-result signing domain. The clarified paragraph rejects this shortcut while leaving independent signatures or a compatible selected scheme/key setup open.

**Two signatures with the same root but different input.** One statement binds AB from S0/runtime R and another binds AC, or AB from another predecessor/runtime. Equal claimed state roots are insufficient. App verifies and groups the complete subject; they cannot contribute to one certificate. Result outputs/material commitments and exact range also remain bound. The current contract passes without another consensus round or Baton approval.

**Direct work completes while only one eligible signature exists.** App has irrevocable AB, validated exact effects and a deterministic selected commitment. It can apply/persist through its writer and ACK covered Updates while the result certificate remains incomplete. No `f+1` wait is introduced into direct durability or ACK (`baton/interfaces.md:135`, `execution/interfaces.md:67,73`). Larger signing ranges cannot force accumulation beyond the delivery window while withholding every ACK.

**Valid certificate, missing outputs or material.** A normal validator receives sufficient matching result authorization but cannot obtain the state delta/checkpoint or retained outputs for that subject. The target can be authenticated, but local adoption/read readiness and ACK remain unavailable from that certificate alone. Valid direct work continues. A reached-target sync notification also does not substitute for completed reconstructed/persisted DB and full output/result validation.

**Certificate before canonical input, or for a longer range.** AB is locally irrevocable, but a valid peer certificate claims ABC. App cannot settle C's unresolved order or slice ABC's certificate into an AB certificate. It keeps the target pending/recovers ordering, continues valid direct work, and adopts only a matching authorized range. Current state-sync and certification text state these conditions; no new callback is required.

**Direct apply races with import preparation.** Import prepares AB material while direct writer durably reaches AB, or moves to a later exact prefix. Candidate readiness does not bypass a fresh predecessor check. The one writer recognizes already-covered exact input or selects valid next work; it cannot apply an obsolete AB delta over the new state. Mutable direct I/O is not canceled by advisory import preference. Existing writer/access and durable-completion ownership covers the race without another commit service.

**Import then signature amplification.** App imports certified AB, relays the original certificate, then directly executes C from that canonical checkpoint. It cannot add a new own direct-execution signature to AB merely because it imported it, but can sign the later directly validated range. Crash recovery preserves imported provenance; a recovered root alone cannot restore direct-signing evidence. Current docs pass.

**Valid native floor, missing App state.** `install_floor` can authenticate the floor's L-QC/history/frontiers, but it does not authenticate or install QMDB execution state. App cannot advance delivery over unestablished durable App work merely because native verification succeeded. For fresh namespace `Start::Floor`, caller authentication and snapshot-bound positive monotone `floor_generation` are real existing startup requirements (`marshal/config.rs:163-186`), distinct from App worker generations. Current startup text preserves this distinction.

**Durable imported AB, Marshal cursor still behind.** App persists imported provenance, state, outputs and exact applied index/block, then signals ACK. Crash before Marshal cursor persistence can redeliver AB. App validates its recovered exact durable linkage and ACKs without applying again or changing provenance. Existing QMDB/journal/metadata mechanisms support persistence, but selecting the matching multi-store App recovery checkpoint remains implementation work; no atomic cross-store guarantee is inferred.

## Minimality and remaining choices

One App-owned result handler can use authenticated P2P, concrete crypto subjects/primitives, QMDB sync/Source and the existing canonical writer. Optional collector/buffered broadcast are transport conveniences, not mandatory ResultService, verifier, relay or consensus layers. The local trusted Marshal Update remains ordinary ordering authority; an external consumer/peer certificate needs its own exact evidence binding, not a duplicate verifier in every local callback.

Keys, crypto format, execution-statement encoding/domain, eligible epoch transitions, deterministic root/batch rules, signing boundaries, material format/retention, import preference and multi-store recovery linkage remain open implementation choices. This review selects none. It also does not treat historical external ecosystem implementations as current native guarantees.
