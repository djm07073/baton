# Block propagation and custody reuse — first wave

Research date: 2026-10-04. Scope: source inspection and proposed documentation replacements. No protocol implementation, benchmark, dependency change, canonical documentation edit, external checkout edit, commit, push, or GitBook write occurred. The native Multimmit baseline remains `534af0ede48affd35b2111522527547b4cc9bf72`.

## Main finding

Replace descriptions of a bespoke BlockService dissemination, cache, fetch/retry, and storage engine with an explicit assembly of existing Commonware primitives. Both Tempo and Alto already assemble the full-block `commonware_broadcast::buffered::Engine` and Commonware Marshal/storage infrastructure. These concrete applications demonstrate the intended composition. For Baton on the pinned Multimmit engine, reuse the **generic buffer, generic P2P resolver, archives and existing Automaton/Relay/Reporter callbacks directly**, then implement a narrow application adapter for body construction, context binding, custody verdicts and retention handoffs.

Do not advertise an unchanged `marshal::standard::{Inline, Deferred}` or Marshal actor as the Multimmit adapter. At the pinned native revision, Marshal documents Simplex-only operation and at-most-one-notarization-per-view assumptions; its wrappers require `simplex::types::Context` and use Simplex relay plans, certification gates and finalizations. Multimmit has producer-lane Context and `Relay::Plan = ()`. This is an observed API boundary, not a search-based claim that Commonware lacks block primitives. [Native Marshal limitations](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/consensus/src/marshal/mod.rs#L61), [Inline type bound](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/consensus/src/marshal/standard/inline.rs#L223), [Deferred type bound and durability](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/consensus/src/marshal/standard/deferred.rs#L471), [Multimmit example application](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/examples/log-multimmit/src/application/actor.rs#L36).

The public Baton `BlockService` responsibility may remain a project-facing application contract, but it should not imply a new network/storage implementation. The required adapters should explicitly delegate to the upstream handles rather than duplicate their algorithms. This first pass does not choose a new public trait count or fill open policy cells.

## Actual-chain call graphs

### Tempo: full-block broadcast with backend custody

1. `Builder::try_init` restores Marshal with `alias::marshal::init`, obtains its finalized floor/tip, and initializes the execution attachment from them. [engine.rs L152](https://github.com/tempoxyz/tempo/blob/61c979a524f9af5de9c540a0088c429a44741e4c/crates/consensus/src/consensus/engine.rs#L152).
2. `buffered::Engine::new(context.child("broadcast"), buffered::Config { public_key, mailbox_size, deque_size, peer_provider, priority, codec_config })` creates a `buffered::Mailbox<PublicKey, Block>`. [engine.rs L207](https://github.com/tempoxyz/tempo/blob/61c979a524f9af5de9c540a0088c429a44741e4c/crates/consensus/src/consensus/engine.rs#L207).
3. Application `Inner` implements `commonware_consensus::Application`; `Marshaled::new` chooses standard `Inline` or `Deferred`, then exposes Automaton/Relay/CertifiableAutomaton to each Simplex epoch engine and `Reporter<Update<Block>>` to Marshal. [application/mod.rs L1](https://github.com/tempoxyz/tempo/blob/61c979a524f9af5de9c540a0088c429a44741e4c/crates/consensus/src/consensus/application/mod.rs#L1), [L74](https://github.com/tempoxyz/tempo/blob/61c979a524f9af5de9c540a0088c429a44741e4c/crates/consensus/src/consensus/application/mod.rs#L74).
4. `run` starts the broadcast on its own channel, calls `marshal::resolver::p2p::init` with a separate backfill channel, starts the Executor attachment, then starts Marshal with application/reporters, the broadcast mailbox and resolver. The epoch manager starts consensus with vote/certificate/native-resolver channels. [engine.rs L519](https://github.com/tempoxyz/tempo/blob/61c979a524f9af5de9c540a0088c429a44741e4c/crates/consensus/src/consensus/engine.rs#L519).
5. Finalization certificates use an immutable archive; finalized bodies use `Hybrid`, a prunable hot archive plus Reth backend. Marshal sees the upstream `store::Blocks` contract, not the implementation split. [storage/mod.rs L56](https://github.com/tempoxyz/tempo/blob/61c979a524f9af5de9c540a0088c429a44741e4c/crates/consensus/src/storage/mod.rs#L56), [alias.rs L132](https://github.com/tempoxyz/tempo/blob/61c979a524f9af5de9c540a0088c429a44741e4c/crates/consensus/src/alias.rs#L132).
6. `Hybrid::put` stores body bytes in the prunable archive; `sync` flushes it; `get` first queries the cache, then the execution backend. Eviction follows the **execution backend's finalized watermark**, ensuring the cache retains blocks the backend does not yet own. Its `Blocks::prune` is deliberately a no-op. The cache may temporarily exceed the configured retention count, with extra section rounding. [Hybrid overview](https://github.com/tempoxyz/tempo/blob/61c979a524f9af5de9c540a0088c429a44741e4c/crates/consensus/src/storage/hybrid/mod.rs#L1), [eviction L360](https://github.com/tempoxyz/tempo/blob/61c979a524f9af5de9c540a0088c429a44741e4c/crates/consensus/src/storage/hybrid/mod.rs#L360), [store methods L393](https://github.com/tempoxyz/tempo/blob/61c979a524f9af5de9c540a0088c429a44741e4c/crates/consensus/src/storage/hybrid/mod.rs#L393).

Tempo's backend-driven eviction is an excellent adapter pattern. It is not a generic proof that arbitrary backend eviction is safe: retained obligations, backend readiness and serving coverage still need Baton-specific contracts. Tempo also explicitly describes old backend-pruned history as logically covered even when no longer fetchable; this is not indefinite custody for every old body. [Hybrid gap/pruning explanation L51](https://github.com/tempoxyz/tempo/blob/61c979a524f9af5de9c540a0088c429a44741e4c/crates/consensus/src/storage/hybrid/mod.rs#L51).

### Alto: full-block broadcast with immutable finalized archives

Alto constructs `buffered::Engine` using a bounded codec derived from its configured block size. It then opens immutable archives for finalizations and finalized blocks, initializes the Marshal actor, wraps its application in standard Deferred, and supplies the same wrapper as consensus Automaton and Relay. Its consensus Reporter fans out to Marshal and optional indexer support. [Buffer/archive assembly L177](https://github.com/commonwarexyz/alto/blob/1d87569348b5560699465a72d691d90f18affb9c/chain/src/engine.rs#L177), [Marshal assembly L273](https://github.com/commonwarexyz/alto/blob/1d87569348b5560699465a72d691d90f18affb9c/chain/src/engine.rs#L273), [wrapper and engine config L341](https://github.com/commonwarexyz/alto/blob/1d87569348b5560699465a72d691d90f18affb9c/chain/src/engine.rs#L341).

The run path starts buffer, Marshal and recovered indexer work before consensus to handle replayed events. Alto's application acknowledges `Update::Block` directly when no backfiller is attached; this is appropriate for its own minimal application but is **not** a durable state-apply ACK contract for Baton. [startup L462](https://github.com/commonwarexyz/alto/blob/1d87569348b5560699465a72d691d90f18affb9c/chain/src/engine.rs#L462), [application report L148](https://github.com/commonwarexyz/alto/blob/1d87569348b5560699465a72d691d90f18affb9c/chain/src/application.rs#L148).

The buffer itself only caches untrusted peer messages, bounded per sender and evicted when peers leave `latest.primary`. `get` is local cache lookup; `subscribe` waits for local availability. Its Producer serves `Bytes`, so it does not require a Simplex Block or QMDB runtime. Its Consumer separates invalid peer data, completed delivery, ambiguous valid responses and no-longer-needed work. ## Custody, restart and retention obligations

1. **Custody requires the actual archived object.** Immutable Archive puts are uncommitted until sync succeeds; restart removes uncommitted lower-layer data. Both ordinary immutable and prunable archive indices are unique and occupied-index writes are no-ops. One Simplex-style global height index cannot represent every lane's same-height Multimmit body. Prunable `put` below the floor can also succeed without storing. Validate exact body presence under the selected schema, preserve idempotence and prevent conflicting-index replacement. `MultiArchive` is an existing capability for duplicate indices, not an automatic schema choice. [immutable uniqueness/durability](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/storage/src/archive/immutable/mod.rs#L6), [prunable uniqueness](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/storage/src/archive/prunable/mod.rs#L32), [prune-floor no-op](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/storage/src/archive/prunable/mod.rs#L97).
2. **Native restart rechecks application custody.** Multimmit's startup calls Automaton verification on recovered `(producer Context, payload)` requirements before dependent consensus authority becomes live. Start body archive/serving/fetch attachments before native startup awaits these verdicts. A restart cannot use a lost buffered cache as proof of retained bytes. [native recovered-payload gate L265](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/consensus/src/multimmit/engine.rs#L265).
3. **Do not import Simplex's deferred durability timing.** Native standard Deferred explicitly returns a staged digest before durability, then waits at its certify gate. Multimmit's producer callback and DA/custody rules need their own correct gate; a Deferred-style early digest is not a drop-in replacement for Baton's documented durable StoredBody success. [Deferred timing L488](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/consensus/src/marshal/standard/deferred.rs#L488).
4. **Peer-set transitions affect fetchability.** Generic resolver outbound requests use `latest.primary`; targeted fetches do not automatically fall back to other peers. If a retained body is only on an old committee, a targeted old peer may no longer be eligible. Application peer-provider/custody handoff must preserve serving coverage without replacing native authority. Use ordinary `fetch` to clear targets when policy requires wider retry. [resolver targeting L27 and peer selection L67](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/resolver/src/p2p/mod.rs#L27).
5. **Bound resource work beyond mailbox_size.** Generic resolver's active serve futures are unbounded; its Producer is responsible for limiting concurrent serving, and network quotas limit request pressure. Buffered ingress also has overflow behavior; mailbox capacity alone should not be called a universal memory bound. Preserve existing open budgets. [serve responsibility L77](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/resolver/src/p2p/engine.rs#L77), [buffer ingress overflow L47](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/broadcast/src/buffered/ingress.rs#L47).
6. **Retire and prune remain separate.** A local relay request is not remote delivery/custody. The native Relay trait has no retire method; an added native lifecycle handoff remains an adapter contract. Any body release must satisfy native recovery/custody, ordered delivery, execution branch, query and state-sync serving references. Neither buffer eviction nor a Marshal view-retention setting proves these obligations are discharged.
7. **Ordering delivery is still a different adapter.** Standard Marshal supplies ordered at-least-once delivery from Simplex finalizations. Sparse Multimmit artifacts cannot be substituted as if they already described the exact dense merged order, authenticated frozen policy interpretation and durable Executor delivery cursor. Preserve irrevocably-empty skipping, unresolved-slot blocking, terminal identity and exact-prefix obligations. This report supplies body primitives, not a solution to Multimmit's native prefix-adoption/continuation bridge.

## Minimum BlockService footprint

Treat **BlockService as the logical body attachment**, not a requirement to introduce a custom public trait, independent actor, new transport engine or parallel state machine. Its smallest necessary implementation footprint is application-specific body construction/codec, native header/body mapping, validated durable archive custody, and retention glue. Implement upstream callbacks directly over the existing primitive handles. A concrete shared attachment object can hold those handles and a narrow correlation table; an additional actor is justified only by an actual ownership or scheduling need.

| Existing custom surface in Baton's Rust page | Minimum replacement | Custom logic that cannot be removed |
|---|---|---|
| `BlockService::build(context)` | Implement upstream `Automaton::propose` directly; invoke TxPool selection/body construction, validate producer context, archive and sync, send digest over native oneshot | Application body format/limits; stable body/context commitment; custody success; cancellation-safe local construction |
| `BlockService::verify(context,digest)` | Implement upstream `Automaton::verify` directly; check retained body, subscribe to buffer, invoke generic resolver if missing, validate and sync, send stable verdict | Native producer-context validation and required-parent custody; local error semantics; no false for temporary absence |
| `BlockService::fetch(block_ref)` | Use existing `buffered::Mailbox::{get,subscribe}` plus `Resolver::{fetch,fetch_all}` or `TargetedResolver::fetch_targeted`; resolver Consumer completes the correlated local readiness request after validation/custody | Convert BlockRef to exact fetch key/subscriber; bind accepted signed header to body; coordinate who still needs data. This is an adapter/wait boundary, not another network fetch engine |
| `BlockService::commitment(body)` | Use upstream `Digestible::digest` on the body type | Define canonical codec/commitment semantics and distinguish native signed header ID from body digest |
| `BlockService::publish(digest)` | Implement upstream `Relay::broadcast(digest,())` directly; resolve locally staged/archived body and call `buffered::Mailbox::broadcast_shared` | Digest-to-body mapping and any actual native-lifecycle publication obligation; local admission failure handling. No custom generic broadcast engine |
| `BlockService::on_retire(retired)` | Narrow native lifecycle → body retention-reference update; archive prune only after release requirements are met | Exact lifecycle/export bridge is still needed; Relay has no retire callback; custody/history/branch/query/state-sync obligations must be retained |
| Header notification/intake | Implement upstream `Reporter::report` directly; match accepted authenticated producer artifact with body readiness and hand candidate to Baton | Header identity/context join, bounded local correlation, and retry of missed opportunistic notices without a native ACK gate |

The body type implements upstream codec/Digestible traits. The fetch attachment implements upstream `commonware_resolver::p2p::Producer` and root `Consumer`, and uses the same authenticated peer provider/blocker/channel infrastructure as other app services. The storage attachment invokes upstream Archive APIs. These are the explicit adapter boundaries; they must not be relabeled as a ready-made Commonware BlockService primitive.

Proposed call graph, where arrows describe adaptation rather than new engines:

```text
Multimmit Automaton::propose(Context)
  -> TxPool selection -> application body codec/context binding
  -> upstream Archive put + successful sync + exact custody
  -> native oneshot digest

Multimmit Relay::broadcast(digest, ())
  -> retained/staged body lookup -> buffered Mailbox::broadcast_shared
  -> buffered Engine -> authenticated body channel

Multimmit Automaton::verify(Context, digest)
  -> upstream Archive / buffered Mailbox lookup-subscription
  -> generic resolver Mailbox::fetch when missing
  -> resolver Engine -> authenticated fetch channel
  -> app Producer reads body archive / app Consumer checks exact key/context
  -> Archive sync and exact custody -> native oneshot true

Multimmit Reporter::report(accepted producer artifact)
  + body-ready event -> exact signed-header/body join -> Baton candidate intake

native custody/history retirement + local retained references
  -> retention glue -> Archive prune / backend serving handoff when permitted
```

Retire the redundant generic fetch/broadcast/caching/retry engines in the design. Retain application semantics where primitives deliberately stop: construction, verification and identity/context mapping, durable body presence, native retirement authority and serving obligations. Document this direct wiring now; changing or deleting a public Rust trait is a separate interface synchronization decision under the user's latest architecture.

### Independent-review questions for this footprint

1. Can an external app consume native `marshal::resolver::handler::Receiver`? Verify `recv`/`try_recv` visibility at the native pin, then reject any assembly claiming the Marshal resolver initializer is directly an external body service. Confirm generic resolver Producer/Consumer wiring instead.
2. Can two Multimmit lanes or competing bodies share a height/index? Test the proposed *schema reasoning*, not a toy protocol: ordinary Archive occupied-index writes are no-ops; prunable writes below the floor can be no-ops. Does every reported custody success establish the exact expected body after sync, with an injective index or explicitly appropriate multi-index representation?
3. Do callbacks preserve the native live/recovery context, pending-versus-invalid distinction and producer-parent custody gate? Does any imported Simplex Deferred path return a digest before the Multimmit custody boundary?
4. Does the direct Relay delegate report only local broadcast admission? Is any claimed remote delivery, custody ACK, retry-until-retire guarantee or mandatory new actor unsupported by the existing primitive?
5. Does header/body intake distinguish body digest, native header block reference and full accepted-artifact ID, and avoid interpreting a body-ready event as cut inclusion?
6. Does retention account for recovery, exact ordered delivery and peer serving after committee changes, rather than simply copying Tempo's Reth watermark or Marshal's view retention? Is the native retirement bridge presented as an unresolved adapter rather than a current Relay method?
7. Does the body attachment remain independent of Stateful and Executor-owned execution semantics, while Storage owns roots/apply/durability under the latest user correction? Does any new role duplicate upstream algorithms?
