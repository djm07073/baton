## Reader-relevant finding

Future Storage/E2E fixtures can use the **actual selected QMDB** under public `commonware_runtime::deterministic` and `commonware_runtime::mocks::DelayedSyncContext`. A new fake DB or general fault engine is unnecessary for controlling flush completion, repeating a run from synced storage, or injecting native storage faults. This is a source-compatible assembly candidate, not a compiled Baton fixture or an implementation/safety claim.

The native pin already distinguishes two useful sync-delay mechanisms:

- `PendingSyncs::default()` parks each `start_sync` completion **before** its inner sync runs. An armed one-shot gate also blocks a blocking `sync`/tracked synchronous write before its inner sync. Release helpers let the future proceed; they do not themselves prove the covering database or Baton metadata is durable.
- `PendingSyncs::completion_delayed()` starts the inner sync immediately and then parks completion. For the deterministic memory backend, that lets a fixture distinguish **durable bytes with undelivered completion** from genuinely unsynced state. It is native-only in these inspected versions: release `v2026.9.0` does not expose this constructor. Do not infer all inner backends complete immediately merely because `start_sync` has started.

Exact public code and ownership are at [native mocks: delayed context/blob](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/runtime/src/mocks.rs#L504), [start/park/await order](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/runtime/src/mocks.rs#L622), and [completion-delay constructor and one-shot gate](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/runtime/src/mocks.rs#L749).

## The recovery boundary matters

`start_and_recover` runs until the root future returns, clears outstanding tasks/futures, drops the root, and only then constructs a checkpoint. If the run itself panics, cleanup runs and the panic is resumed; it does **not** return a checkpoint from that panic path. A future fixture should return normally at a chosen abrupt-stop boundary while unfinished children are still present, then consume its returned checkpoint, rather than assuming `catch_unwind` yields that checkpoint. Escaping runtime/context references is rejected by explicit reference-count assertions. [Native cleanup/checkpoint construction](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/runtime/src/deterministic.rs#L686).

The recovered runtime retains RNG/time/deadline/auditor/storage, but does not inherit pending tasks, network connections, shutdown signaler or live unsynced blob buffers. The retained storage/fault-config wrapper is reused; future tests can explicitly reset `*context.storage_fault_config().write()` for a clean recovery inspection. Its returned shared config changes **subsequent** operations; it does not cancel an in-flight operation or identify a Baton commit boundary. `Context::recover` is private, so the external restart seam is `Runner::from(Checkpoint)`. [Native recovery implementation](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/runtime/src/deterministic.rs#L1005), [public dynamic fault config](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/runtime/src/deterministic.rs#L1094).

Native memory blobs separate open-handle working contents from a partition map updated by `sync_inner`; reopening sees that map. `storage_audit` hashes retained partition contents, not outstanding live blob buffers, and is neither a QMDB canonical root nor a linked application receipt. Open/create and remove mutate the partition map directly. The deterministic model is therefore a specific simulation, not a proof of filesystem/device crash behavior. The `runtime::storage` module is **private** despite its nested public declarations: outside crates should import public deterministic reexports and mocks, not `commonware_runtime::storage::memory`/`faulty`. [Private module/public exports](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/runtime/src/lib.rs#L29), [memory map/open](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/runtime/src/storage/memory.rs#L19), [working-buffer sync](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/runtime/src/storage/memory.rs#L169).

Native `FaultConfig` has per-operation `Option<f64>` rates. A failed write can write a prefix, sync that prefix, and return an error; a partial resize similarly syncs an intermediate length before error. A synchronous write whose sync is injected to fail can still update the open buffer. So an error does not mean no effects; a successful unsynced write does not mean crash durability. No rate or exhaustive device-failure model is adopted here. [Native fault fields](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/runtime/src/storage/faulty.rs#L27), [partial-write/resize and sync errors](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/runtime/src/storage/faulty.rs#L321).

## Minimal future E2E wiring; no new public trait

1. Construct the selected real DB from a `DelayedSyncContext { inner: context, pending: PendingSyncs::default() }` under `Runner::new(config)`. Constructor config, schema, hash, runtime Strategy and backend remain open. This is a noncompiled type/ownership recipe, not an executable sketch.
2. Drive existing unmerkleized change preparation and selected merkleization/apply via the application's **existing** Storage contract. Keep exact base/order/runtime/provenance, public `validate_batch` preflight scope, and the same shared writer/fences. Native `apply_batch` publishes/append-writes but explicitly does not guarantee durability. `commit`, `sync`, or successfully awaiting `start_sync`'s handle establish their documented QMDB durability boundary; `sync` additionally guarantees the described recovery work is unnecessary. [Native apply scope](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/storage/src/qmdb/any/batch.rs#L2727), [commit/start-sync/full-sync distinction](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/storage/src/qmdb/any/db.rs#L819).
3. For unsynced abort, observe the relevant `DeferredSync::blocked`, leave its gate unreleased, and end that runtime's root. For durable-but-unobserved completion in the native deterministic backend, use `completion_delayed`, separately observe actual inner progress/retained state, and leave outer completion/ACK outstanding. For a lost **delivery** ACK after durable apply, first establish the complete application receipt predicate and then suppress/cancel the optional local ACK path; a sync gate alone is not an ACK fault. No fixed delay/timeout or new receipt encoding is selected.
4. Reopen the same physical partitions through a new `Runner::from(checkpoint)` context, rebuild DB/services from retained durable material, and check the full state/output/exact cursor/provenance link before ACK/read readiness. Do not reuse the old `Shared`, open blobs, task handles or worker authority as the recovered writer. Existing `Shared` loses its database permanently when a by-value mutation is interrupted without `put`, which is a restart case, not a roll-back/reinsert permission. [Shared write-slot semantics](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/glue/src/stateful/db/mod.rs#L113).
5. Exercise verified imported material through the same application guards: verified full execution certificate plus locally applicable material before stopping unfinished work; direct/imported signing provenance; no imported own-signature; exactly one canonical writer. Neither `PendingSyncs` nor QMDB validates these application predicates. Existing barrier failure semantics also matter: `durable` returns false for Closed/Aborted handles, while ordinary deferred I/O errors panic after state has advanced. Do not translate an injected I/O error into harmless `false`. [Barrier](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/glue/src/stateful/db/mod.rs#L449).

## Actual QMDB and chain fixtures: reuse mechanisms, not private suites

Native QMDB has source examples for reopening after an awaited `start_sync`, and for recovering a journal commit newer than the last full-sync boundary. Those helpers are `pub(crate)` inside `#[cfg(test)]`: they reopen a DB within the same runtime and are not themselves a simulated process-crash proof. Use their assertions/root/key/size comparisons as source patterns and public DB operations for future fixtures. `qmdb::any::traits` is gated by test or `test-traits`; the Current bitmap inspection trait is separately gated; the Current `tests` module remains `#[cfg(test)]`. Enabling `test-traits` does not export the entire upstream test suite. [Native Any test module/gates](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/storage/src/qmdb/any/mod.rs#L96), [commit/reopen and start-sync fixtures](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/storage/src/qmdb/any/mod.rs#L571), [Current test boundaries](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/storage/src/qmdb/current/mod.rs#L485).

Constantinople's held-ACK `RestartBarrier` stores `Exact` acknowledgements, clears them on restart, and separately records recovered finalization and observed processed height. Its property rejects processed-height advancement before ACK despite higher recovered finalization. This is an actual-chain illustration of the distinct failure boundaries, but `RestartBarrier`, `TestReporter` and the property are crate-private inside its gated tests; they are not imports or an application durable-state proof. [Chain held-ACK fixture](https://github.com/commonwarexyz/constantinople/blob/3b6c92e76bf582855615844a4175b8304808f6a9/crates/engine/src/tests/common.rs#L42), [processed-height assertion](https://github.com/commonwarexyz/constantinople/blob/3b6c92e76bf582855615844a4175b8304808f6a9/crates/engine/src/tests/properties.rs#L132), [test module gate](https://github.com/commonwarexyz/constantinople/blob/3b6c92e76bf582855615844a4175b8304808f6a9/crates/engine/src/lib.rs#L30), [separate Commonware graph](https://github.com/commonwarexyz/constantinople/blob/3b6c92e76bf582855615844a4175b8304808f6a9/Cargo.toml#L51).

## Native versus explicit release and receipts

Release corroborates the delayed-sync queue/gates and deterministic checkpoint public concepts, but is not byte/type identical: the native-only `PendingSyncs::completion_delayed` is absent from the entire release mocks file, and release FaultConfig uses `Probability`, `WriteConfig` (prefix/subset retention) and `ResizeConfig` instead of native `Option<f64>` plus partial-rate fields. Those release crash-retention semantics cannot be attributed to native. Any Db's core commit/start_sync source and glue simulate EngineDefinition happened to be byte-identical in this fresh comparison; that does not equate the dependency graph. [Release gate implementation](https://github.com/commonwarexyz/monorepo/blob/d476a2361ce6840d2b9d0aa6fb30a924429046d4/runtime/src/mocks.rs#L925), [release fault types](https://github.com/commonwarexyz/monorepo/blob/d476a2361ce6840d2b9d0aa6fb30a924429046d4/runtime/src/storage/faulty.rs#L35).

Two explicit-version MCP excerpts are checked against **169 zero-based numbered release source lines** in `mcp-source-check.json`; MCP is release corroboration only.
