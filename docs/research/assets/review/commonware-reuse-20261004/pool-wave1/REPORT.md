# Transaction pool and block construction: first source review

Research date: 2026-10-04. This report is a source review and integration proposal, not an implementation, compatibility test, benchmark, or adoption decision. It changes no canonical documentation or policy cell. Generic Bank semantics remain outside Baton’s current scope. Native Multimmit remains pinned to `534af0ede48affd35b2111522527547b4cc9bf72`.

## Finding

A complete transaction pool is not exposed as a Commonware **monorepo primitive** in the explicit `v2026.9.0` MCP inventory reviewed here. That does not mean no Commonware-based pool exists. **Constantinople has an actual chain-specific pool actor** with admission, local duplicate suppression, bounded queues, selection and proposal-outcome bookkeeping. **Tempo uses a Reth pool plus Tempo extensions and a Reth/REVM payload builder**. A separate ecosystem demonstration, `zmanian/commonware-mempool`, exists but its inspected code cannot supply Baton’s custody or canonical-outcome contract. Alto supplies a minimal block construction example, not a transaction pool.

For maximum reuse, Baton should put a thin TxPool application adapter in front of an explicitly selected existing backend and keep BlockService as attachment/codec/custody assembly over Commonware. It should not implement a second generic pool beside that backend. However, no reviewed backend transfers unchanged into the current generic workload and Multimmit’s multiple independently growing producer lanes. Compatibility and application semantics must be assessed before documenting a default.

## 1. Constantinople is a real pool candidate, with important coupling

### Exact attachment API

`constantinople_mempool::TransactionSource<C, P, H>` extends `Reporter<Activity = Update<SealedBlock<C, P, H>>>`. Its `propose(&mut self, parent: &Header<C, H::Digest, P>, round: Round, filled: usize)` returns `Vec<VerifiedTransaction<H>>`. `filled` is already selected encoded signed-transaction bytes; the source must respect remaining transaction bytes while the caller reserves block framing. Speculative prebuilds may ask before the target round is live. [TransactionSource, lines 9–35](https://github.com/commonwarexyz/constantinople/blob/3b6c92e76bf582855615844a4175b8304808f6a9/crates/mempool/src/lib.rs#L9-L35).

The webserver `Mailbox::channel(capacity)` gives a bounded mailbox and actor receiver. `try_submit` provides terminal-status waiting; the internal `try_ingest` path provides admission-result waiting. Its TransactionSource implementation derives `height = parent.height + 1`, ignores round, sends `Message::Propose { height, filled, response }`, and panics if the pool actor mailbox closes. Reporter forwards marshal finalized/tip Updates into the actor. [Mailbox and channel, lines 102–173](https://github.com/commonwarexyz/constantinople/blob/3b6c92e76bf582855615844a4175b8304808f6a9/crates/mempool/src/webserver/mailbox.rs#L102-L173), [propose and Reporter, lines 193–244](https://github.com/commonwarexyz/constantinople/blob/3b6c92e76bf582855615844a4175b8304808f6a9/crates/mempool/src/webserver/mailbox.rs#L177-L224).

### What can actually be reused

- Foreground/background bounded queue accounting and one-proposal foreground reservation. It checks total bytes and proposal bytes and returns explicit admission/terminal statuses. These are implemented policies, not recommendations to adopt them. [configuration, lines 121–140](https://github.com/commonwarexyz/constantinople/blob/3b6c92e76bf582855615844a4175b8304808f6a9/crates/mempool/src/webserver/actor.rs#L121-L140), [admission capacity, lines 596–623](https://github.com/commonwarexyz/constantinople/blob/3b6c92e76bf582855615844a4175b8304808f6a9/crates/mempool/src/webserver/actor.rs#L596-L623).
- Local duplicate tracking using `known_digests: AHashSet<H::Digest>` and `VerifiedTransaction::message_digest()`. Duplicate messages are skipped at admission. Identity is the transaction message digest, not necessarily a hash of all signed envelope bytes. [dedup helper, lines 559–574](https://github.com/commonwarexyz/constantinople/blob/3b6c92e76bf582855615844a4175b8304808f6a9/crates/mempool/src/webserver/actor.rs#L559-L574).
- FIFO **whole-batch** packing. `pop_lane_proposal` examines the front batch; if it does not fit remaining bytes, that lane stops. It does not split the front batch or search smaller later entries. Foreground is selected before background. [selection, lines 402–457](https://github.com/commonwarexyz/constantinople/blob/3b6c92e76bf582855615844a4175b8304808f6a9/crates/mempool/src/webserver/actor.rs#L402-L457).
- Tracking selected message digests in outstanding `ProposedBatch { height, digests }` and resolving matching finalized digests. Unmatched digests remain outstanding until the configured grace window expires, then receive Dropped status. [outcome resolution, lines 461–518](https://github.com/commonwarexyz/constantinople/blob/3b6c92e76bf582855615844a4175b8304808f6a9/crates/mempool/src/webserver/actor.rs#L461-L518).
- Commonware codec/hash/signature/parallel primitives underneath the existing application, rather than replacing them with custom crypto or encoding. The transaction is still Constantinople’s sender/recipient/value/nonce format. [transaction type, lines 134–164](https://github.com/commonwarexyz/constantinople/blob/3b6c92e76bf582855615844a4175b8304808f6a9/crates/primitives/src/transaction.rs#L134-L164), [body verification, lines 16–45](https://github.com/commonwarexyz/constantinople/blob/3b6c92e76bf582855615844a4175b8304808f6a9/crates/application/src/consensus/body.rs#L16-L45).

### Why direct adoption is not established

**Selection is destructive.** Selected entries are popped immediately and removed from queue byte accounting, although their digests remain in the outstanding proposal set. Therefore an unchanged source does not satisfy Baton’s “selection alone does not retire transactions” contract merely because its status remains pending. Baton requires the retention/reselection semantics to be reconciled with local cancellation, retained bodies and canonical execution outcomes. [pop and proposal record, lines 420–432](https://github.com/commonwarexyz/constantinople/blob/3b6c92e76bf582855615844a4175b8304808f6a9/crates/mempool/src/webserver/actor.rs#L420-L432).

**It is not a general peer transaction gossip subsystem.** This reviewed pool receives verified HTTP submissions, exposes an HTTP server and listens to pool mailbox Updates. Its separate relayer forwards to configured validator HTTP endpoints, including background submissions and caller-selected target/fanout controls. Reusing the pool does not automatically provide an authenticated Commonware tx inventory/body exchange protocol. [HTTP actor startup, lines 718–730](https://github.com/commonwarexyz/constantinople/blob/3b6c92e76bf582855615844a4175b8304808f6a9/crates/mempool/src/webserver/actor.rs#L718-L730), [relayer forwarding, lines 455–473](https://github.com/commonwarexyz/constantinople/blob/3b6c92e76bf582855615844a4175b8304808f6a9/bin/validator/src/relayer.rs#L455-L473), [target and fanout, lines 516–532](https://github.com/commonwarexyz/constantinople/blob/3b6c92e76bf582855615844a4175b8304808f6a9/bin/validator/src/relayer.rs#L516-L532).

**Its outcomes are not Baton’s durable canonical execution results.** The actor checks finalized block-body digests against outstanding local proposals. If no local proposals are outstanding, it skips extraction entirely; queued transactions included elsewhere are not globally removed by that branch. This is suitable only with the surrounding chain’s own execution/replay checks, not proof of a generic exactly-once pool. [Update handler, lines 844–892](https://github.com/commonwarexyz/constantinople/blob/3b6c92e76bf582855615844a4175b8304808f6a9/crates/mempool/src/webserver/actor.rs#L844-L892).

**Its block builder executes before constructing committed state roots.** `Application::propose_child` selects transactions, executes against the parent state, drops inapplicable nonce/balance candidates and refills. It then constructs state/transaction roots and verifies complete encoded block size. That is source evidence for how to assemble an application, not permission to move state-dependent execution into Baton’s TxPool or DA-only BlockService. [builder, lines 55–125](https://github.com/commonwarexyz/constantinople/blob/3b6c92e76bf582855615844a4175b8304808f6a9/crates/application/src/consensus/lifecycle.rs#L55-L125), [state-dependent filtering/refill, lines 362–384](https://github.com/commonwarexyz/constantinople/blob/3b6c92e76bf582855615844a4175b8304808f6a9/crates/application/src/consensus/execution.rs#L362-L384).

**It depends on a different Commonware revision** (`92036f4beefedc9817f0954d98fb99e0b52431cb`). Reuse of an unchanged crate is not demonstrated compatible with the adopted native pin. [Cargo, lines 51–67](https://github.com/commonwarexyz/constantinople/blob/3b6c92e76bf582855615844a4175b8304808f6a9/Cargo.toml#L51-L67).

The realistic reuse path is therefore: first assess the existing package at its pinned dependency graph; if generic transaction and lifecycle incompatibility prevents a whole-crate adapter, reuse a maintained/extracted queue/dedup/budget kernel with explicit provenance rather than describing a newly written generic pool as an upstream component. Extraction itself remains new engineering, outside this research task.

## 2. Tempo demonstrates substantial whole-stack reuse for EVM workloads

Tempo’s current tree uses `crates/consensus`; the old `crates/commonware-node` path is stale for this pin. `TempoTransactionPool<Client, EvmConfig>` wraps a standard Reth pool for regular transactions and a Tempo 2D-nonce pool for nonzero nonce keys. It implements Reth’s `TransactionPool` interface, provides merged best-transaction iterators and removes transactions across both pools. [pool composition, lines 1–87](https://github.com/tempoxyz/tempo/blob/61c979a524f9af5de9c540a0088c429a44741e4c/crates/transaction-pool/src/tempo_pool.rs#L1-L87), [best selection, lines 905–930](https://github.com/tempoxyz/tempo/blob/61c979a524f9af5de9c540a0088c429a44741e4c/crates/transaction-pool/src/tempo_pool.rs#L905-L930), [removal, lines 991–1024](https://github.com/tempoxyz/tempo/blob/61c979a524f9af5de9c540a0088c429a44741e4c/crates/transaction-pool/src/tempo_pool.rs#L991-L1024).

### Concrete assembly APIs

`TempoPoolBuilder::build_pool` builds the Reth transaction-validation task executor with provider/EVM config and configured byte/gas/fee limits, wraps it in `TempoTransactionValidator`, creates `Pool::new(validator, TempoTipOrdering, blob_store, pool_config)`, wraps that with `TempoTransactionPool::new(protocol_pool, aa_2d_pool)`, and starts Reth and Tempo maintenance. It offers separate additional stateless and stateful validation hooks; only the stateless hook is analogous to Baton payload analysis. [builder, lines 772–856](https://github.com/tempoxyz/tempo/blob/61c979a524f9af5de9c540a0088c429a44741e4c/crates/node/src/node.rs#L772-L856), [validation hooks, lines 670–735](https://github.com/tempoxyz/tempo/blob/61c979a524f9af5de9c540a0088c429a44741e4c/crates/node/src/node.rs#L670-L735).

`TempoNetworkBuilder::build_network` gets the Reth network builder, optionally adds Tempo’s **finalization certificate** RLPx subprotocol, then calls `ctx.start_network(network, pool)`. Do not call that Tempo certificate gossip module the tx gossip implementation. The transaction path is Reth’s `TransactionsManager<Pool, N>`: incoming eth full transactions/hash announcements, per-peer seen caches, fetches, bounded import work and propagation. [Tempo network assembly, lines 205–226](https://github.com/tempoxyz/tempo/blob/61c979a524f9af5de9c540a0088c429a44741e4c/crates/node/src/node.rs#L205-L226), [Reth transaction manager, lines 271–321](https://github.com/paradigmxyz/reth/blob/038edab20dfff017f7a7502e683c732e5628ad89/crates/net/network/src/transactions/mod.rs#L271-L321).

`TempoPayloadBuilder<Provider>` owns the pool, provider, Reth TaskExecutor and TempoEvmConfig. Its Reth `PayloadBuilder::try_build` supplies `pool.best_transactions_with_attributes(attributes)` to the payload construction loop. That loop handles block gas limits, separate payment/general budgets, encoded RLP block limits, cancellation and EVM execution/replay. These are substantial existing assembly pieces, but they include application-specific decisions. [builder ownership and try_build, lines 135–150 and 238–250](https://github.com/tempoxyz/tempo/blob/61c979a524f9af5de9c540a0088c429a44741e4c/crates/payload/builder/src/lib.rs#L135-L150), [packing limits, lines 573–630](https://github.com/tempoxyz/tempo/blob/61c979a524f9af5de9c540a0088c429a44741e4c/crates/payload/builder/src/lib.rs#L573-L630), [execution and invalid-candidate behavior, lines 654–710](https://github.com/tempoxyz/tempo/blob/61c979a524f9af5de9c540a0088c429a44741e4c/crates/payload/builder/src/lib.rs#L654-L710).

The Commonware consensus application constructs payload attributes for its actual parent and calls `executor.build_proposal(Context, attrs, deferred_extra_data)`. The executor owns the build job; dropping the subscriber tells it the payload is no longer wanted. This is a useful cancellation/ownership pattern, not an existing Multimmit body-custody contract. [consensus-to-builder call, lines 185–237](https://github.com/tempoxyz/tempo/blob/61c979a524f9af5de9c540a0088c429a44741e4c/crates/consensus/src/consensus/application/impl.rs#L185-L237).

Tempo maintenance subscribes to Reth canonical state notifications and uses post-state updates to remove mined 2D transactions, refresh caches, revoke keychain-dependent transactions and evict stale entries. It should be fed from actual canonical execution if adapted, not producer-lane inclusion. [maintenance, lines 475–548](https://github.com/tempoxyz/tempo/blob/61c979a524f9af5de9c540a0088c429a44741e4c/crates/transaction-pool/src/maintain.rs#L475-L548).

### Is Reth generic enough?

Reth calls its pool generic, but explicitly assumes Ethereum nonce, gas and fee information. `TransactionPool::Transaction` must implement `EthPoolTransaction`; `PoolTransaction` extends Alloy’s Transaction and uses Ethereum signed/recovered transaction forms. `EthPoolTransaction` additionally has blob sidecar APIs. A generic opaque Baton transaction cannot be passed unchanged. [pool assumptions, lines 136–161](https://github.com/paradigmxyz/reth/blob/038edab20dfff017f7a7502e683c732e5628ad89/crates/transaction-pool/src/lib.rs#L136-L161), [TransactionPool bound, lines 114–116](https://github.com/paradigmxyz/reth/blob/038edab20dfff017f7a7502e683c732e5628ad89/crates/transaction-pool/src/traits.rs#L114-L116), [transaction bounds, lines 1340–1350](https://github.com/paradigmxyz/reth/blob/038edab20dfff017f7a7502e683c732e5628ad89/crates/transaction-pool/src/traits.rs#L1340-L1350), [blob APIs, lines 1556–1588](https://github.com/paradigmxyz/reth/blob/038edab20dfff017f7a7502e683c732e5628ad89/crates/transaction-pool/src/traits.rs#L1556-L1588).

For an explicitly adopted Ethereum/Reth execution backend, the maximum-reuse path would reuse Reth pool/network/maintenance and the existing payload builder architecture, then implement Baton’s exact-context/native adapters. For the current backend-neutral design, pretending to have adopted Tempo would introduce fees, nonce lanes, Alloy/RLPx, provider and REVM contracts absent from the user’s scope. The Tempo pool Cargo dependencies make that coupling explicit. [pool Cargo, lines 20–45](https://github.com/tempoxyz/tempo/blob/61c979a524f9af5de9c540a0088c429a44741e4c/crates/transaction-pool/Cargo.toml#L20-L45).

## 3. Alto and the separate ecosystem demonstration do not close the gap

Alto’s pinned `ConsensusApplication::propose` consumes an ancestry parent, generates an opaque random load payload of configured size and constructs a Block. Its Input is `()`; no TxPool appears in that path. Verification checks payload length and timestamps. Alto remains a useful example for Commonware application wiring and marshaled ancestry, not a reusable complete mempool. [Alto application, lines 51–101](https://github.com/commonwarexyz/alto/blob/1d87569348b5560699465a72d691d90f18affb9c/chain/src/application.rs#L51-L101), [block’s opaque data, lines 21–40](https://github.com/commonwarexyz/alto/blob/1d87569348b5560699465a72d691d90f18affb9c/types/src/block.rs#L21-L40).

The separately owned `zmanian/commonware-mempool` demonstrates Commonware Simplex consensus plus Mosaik streams. Its README describes two P2P stacks and lists full block broadcast and source wiring as future work. [README](https://github.com/zmanian/commonware-mempool/blob/a80b86e22a74322cf4c29b07973f00711dbc4373/README.md).

The source shows why it cannot be directly adopted as a Baton pool/body service: public tx ingress simply `push_back`s into an in-memory VecDeque; Relay only logs; Verify returns true without body/custody validation. Most significantly, `Message::Propose` publishes a message named FinalizedBlock before returning the proposal digest, while its consensus Reporter only logs genuine finalization. Those messages are not evidence of irrevocable order and cannot drive Baton canonical cleanup. [ingress, lines 234–244](https://github.com/zmanian/commonware-mempool/blob/a80b86e22a74322cf4c29b07973f00711dbc4373/src/mempool.rs#L234-L244), [Relay/Reporter, lines 106–143](https://github.com/zmanian/commonware-mempool/blob/a80b86e22a74322cf4c29b07973f00711dbc4373/src/mempool.rs#L106-L143), [proposal confirmation and verification, lines 416–441](https://github.com/zmanian/commonware-mempool/blob/a80b86e22a74322cf4c29b07973f00711dbc4373/src/mempool.rs#L416-L441).

This is a legitimate ecosystem survey result; rejecting direct adoption follows inspected source semantics, not the project’s name or age.

## 4. Multiple producer lanes change transaction lifecycle

Native Multimmit orders producer headers/bodies through independently growing lanes. A transaction propagated to several producers can appear in several authentic bodies. Pool-local duplicate suppression prevents repeat admission in one process; it cannot prevent that cross-producer occurrence. Neither a proposal-pop queue nor a single EVM pending nonce chain solves the global rule by itself.

This is an integration inference from native producer-context separation and the reviewed pool APIs, not an executed Baton trace. The current Baton docs correctly leave application duplicate semantics blank. A candidate design must specify, without altering authenticated body order:

1. Transaction identity and replay key; message digest, signed-envelope digest and application request identity are distinct choices.
2. Whether repeated occurrences fail, no-op or produce some application-specific deterministic outcome.
3. Exact canonical input-state scope of any replay/dedup state, including speculative branches and crash recovery.
4. Selection/reservation retention versus durable body custody, and canonical pool cleanup after Executor’s durable outcomes.
5. How native producer parent and global canonical execution parent are represented separately.

Do not silently remove duplicate transactions from delivered block bodies. Body commitment and authenticated segment interpretation must remain exact. If application execution suppresses a second effect, it must do so deterministically in Executor while accounting for the occurrence/outcome; local pool cleanup is only candidate lifecycle. Do not equate cross-producer overlap with incorrect native order or assume an application replay policy that has not been adopted.

## 5. Maximum-reuse assembly proposal

| Stage | Reuse first | Baton-specific connection |
|---|---|---|
| Ingress/admission | Selected pool’s admission, dedup, retained entries, configured limits; Commonware codec and crypto where compatible | Static payload features and classify hook remain in TxPool; origin/source and pure policy integration |
| Transaction transport | Existing chain transport if its workload/backend is explicitly adopted; otherwise Commonware authenticated P2P logical channels and available broadcast/resolver components | Chosen tx schema, identity, inventory/body policy, admission gating and per-plane budgets; no evidence of a ready-made generic tx protocol |
| Producer batch | Existing pool selection/iterator and budget accounting | Exact native producer Context, selected transaction/body correspondence, cancellation/reservation lifecycle |
| Body construction | Existing codec/size tools and selected builder’s compatible packing kernel | Final framing/context binding, full encoded-body limit, digest; no stateful prefilter default |
| Custody/availability | Commonware archive/storage, buffered broadcast and resolver | Covering sync, exact expected digest/context, parent material, retention and native callback completion |
| Canonical execution/outcomes | Existing execution backend and pool maintenance API where semantics match | Orderer → Executor exact range, durable canonical outcome → TxPool update; no Baton gate or producer-inclusion shortcut |

The thin application adapter is necessary even when reusing a complete pool: `TxPool::admit/select/on_proposal/on_commit` are Baton integration contracts, not additional storage/network engines. `BlockService::build/verify/fetch/commitment/publish/on_retire` remain custody/attachment integration over upstream components, not a claim that Commonware ships BlockService.

### Concrete candidate tradeoffs

| Candidate | Reuse value | Required adaptation / reason not a default |
|---|---|---|
| Unchanged Constantinople mempool crate | Actual bounded actor, HTTP admission, local dedup, whole-batch selection/status logic | Fixed chain transaction/Header/SealedBlock types; different dependency revision; destructive selection; height/grace outcomes; no generic Commonware tx gossip |
| Constantinople maintained kernel reuse | More modest dependencies than full EVM stack; reusable queue/dedup/bytes/status patterns | Extraction/generalization is new work; retention/outcome semantics must change; cannot call the result an existing primitive |
| Reth pool + network + builder architecture | Largest verified reuse surface for EVM: indexing, replacement, retention limits, best iterators, seen caches, fetching, propagation, canonical maintenance, execution-aware packing | Ethereum transaction/account/fee/provider assumptions and separate RLPx stack; generic workload mismatch; Multimmit producer/canonical-parent integration remains |
| Alto example | Small readable application/ancestry/block wiring | Opaque random payloads, no real pool |
| Mosaik/Commonware demo | Illustrates dual-stack typed streams and source routing | Missing custody/validation and premature “finalized” confirmation; incompatible direct lifecycle; no maturity inference from demonstration claims |

### Proposed documentation/trait simplifications

- Keep the adopted five public application traits. Do not add PoolStorage, TxGossip, TxPolicy, Runtime or a custom replacement consensus trait merely to expose the reused backend’s internals.
- Replace any broad “Commonware has no mempool” phrasing with the scoped inventory conclusion plus the explicit chain/ecosystem candidates above.
- Describe TxPool as **an adapter over a selected existing pool backend**, with backend choice left open. Document exactly what the selected implementation provides, rather than presenting all candidate indexing/eviction/packing as fresh Baton work.
- Explain that `Selection` supplies producer context and limits, while canonical maintenance consumes Executor outcomes; it must not infer global application state from a producer-lane parent.
- Keep `on_proposal` separate from `on_commit`; reconcile backend destructive selection through reservations/body references or explicitly selected cancellation behavior before narrowing the interface.
- Keep static `analyze/classify` inside TxPool. Existing validation/filter hooks are integration patterns; router versus packing-time placement remains blank, and stateful nonce/balance checks do not become static analysis.
- Name upstream callback, archive, broadcast and resolver APIs below BlockService, and call only the binding/custody logic proposed application work. Existing Reth/Constantinople execution-aware builders are references, not adopted DA verification semantics.

## Remaining open choices

The workload and transaction representation must be chosen before a whole pool package can be selected honestly. Existing blank policy cells stay blank: router versus packing filters, concrete pool backend, transaction identity/signing domain, duplicate effects, limits/order, tx wire protocol, admission durability, cancellation/reselection and canonical retention.

A later review should check license/dependency graph, published-crate status, mailbox error/cancellation behavior, cross-lane resource bounds and restart lifecycle against the actual selected backend. Source type compatibility, custody timing, exact transaction-outcome routing and multi-producer replay semantics require integration verification; none was executed here.

## 6. Recommended development sequence and import/adaptation recipes

The recommended next development step is **a backend-fit and API-compatibility spike on the existing Constantinople pool kernel**, bounded to the generic pool problem; an EVM workload decision should instead trigger **whole Reth subsystem reuse**. Neither path should begin by writing a fresh Baton queue, generic gossip manager or packing engine. This is a recommendation for future authorized implementation, not work performed or an adopted policy here.

### Recipe A: generic payloads, preserve the small existing pool

1. Evaluate `constantinople_mempool::{TransactionSource, webserver::{Actor, Config, Mailbox}}` at the historical source pin. Public `Mailbox::channel(capacity)`, `Actor::new(...)`, `Actor::start(listener)` and `Mailbox::try_submit(...)` are real importable entry points. The TransactionSource/Reporter implementations supply the existing actor request/update bridge. The unchanged package is acceptable only if its concrete transaction/body types and dependency revision are compatible with the selected workload.
2. If those fixed chain types fail the fit check, adapt **the existing implementation pieces**, not their assumed API: `PoolLane`/`PoolEntry`, `new_transactions`, `can_admit_submission`, `total_bytes_for`, `pop_lane_proposal/pop_proposal`, and the outstanding-digest/status machinery. These helpers are private in the inspected actor; they cannot be imported as public generic primitives without an extraction/upstream change. Preserve their source provenance and testable guarantees when adapting.
3. Expose the already implemented ingestion-result path through a thin admission bridge. Existing `try_ingest` is `pub(super)`; public `try_submit` resolves terminal status, which must not cause Baton `TxPool::admit` to wait for canonical completion. This is an actual API mismatch to resolve, not a reason to recreate queue ownership. [existing visibility and completion types](https://github.com/commonwarexyz/constantinople/blob/3b6c92e76bf582855615844a4175b8304808f6a9/crates/mempool/src/webserver/mailbox.rs#L115-L173).
4. Put `analyze/classify` in this TxPool adapter. Run payload-only analysis using configured pure hooks and cache the result beside or by the selected backend’s entry identity if appropriate. Analysis version/cache schema and whether classification runs on ingress or packing remain open. No second policy trait is needed; no nonce/balance/provider reads may be smuggled into the static hook.
5. Rebind local proposal correlation to native producer context/body identity rather than a single `parent.height + 1`. Reconcile selection ownership and cancellation before exposing `TxPool::select`: the backend’s pop cannot become canonical retirement. Reuse byte budget accounting while letting BlockService reserve complete body framing and establish custody.
6. Feed `TxPool::on_commit` from Executor’s durable canonical outcomes. Adapt the existing digest-watcher/status machinery to these outcomes instead of invoking unchanged marshal Update cleanup on lane acceptance, native retirement or proposal-time notifications. Whether failed/replayed/expired candidates are retained or dropped remains the selected application policy.

This keeps the queue, local dedup, byte accounting and selection as a reused backend kernel and leaves Baton with context, static-feature and lifecycle adapters. It does not adopt Constantinople’s transfer semantics, foreground priority, grace timer or FIFO whole-batch policy automatically.

### Recipe B: EVM-compatible workload, reuse the full Reth subsystem

Import the existing `reth_transaction_pool::{Pool, PoolConfig, TransactionValidationTaskExecutor, TransactionOrigin, TransactionPool, BestTransactions}` APIs and the Reth `TransactionsManager` network service. Build the pool with the selected validator/order/blobstore configuration, reuse `add_transaction/add_external_transactions`, `best_transactions_with_attributes`, removal/canonical-state maintenance and existing network announcement/fetch/seen-cache logic. Tempo’s exact construction shows a working assembly route.

Prefer base Reth first; add `TempoTransactionPool` only if Tempo nonce lanes, custom transaction types, fee AMM/keychain and related application behavior are explicitly required. A generic Baton workload should not pay for those chain extensions merely because Tempo uses Commonware consensus. Both base Reth and Tempo carry Ethereum transaction/account/provider requirements; adopting that stack changes workload scope and does not supply the Native Multimmit exact-order adapter.

Keep BlockService DA/custody verification distinct from a Reth builder’s pre-execution. If the EVM backend is chosen, reuse its execution-aware builder through Executor-owned execution work, then return the exact body to BlockService’s custody attachment. This routing is proposed integration; no source proves that the reviewed builder already obeys Baton’s parent-linked execution and result-certificate contracts.

### Recipe C: standard Commonware services when the candidate pool transport is unsuitable

The native pinned `broadcast::buffered::Engine` maintains a bounded per-peer payload cache and stores redundant messages once across peers. Its real `Mailbox` API includes `broadcast_shared(Recipients<P>, Arc<M>)`, `get(digest)` and `subscribe(digest)`, with `M: Digestible + Codec`. This removes a need to write another duplicate **payload cache and broadcast engine**. It does not provide a stream of unknown transactions for admission: get/subscribe require a known digest. [cache semantics](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/broadcast/src/buffered/mod.rs#L1-L23), [Mailbox APIs](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/broadcast/src/buffered/ingress.rs#L91-L143).

Use `commonware_resolver::Resolver::{fetch, fetch_all, retain}` with keyed subscribers to reuse fetch lifetime and response delivery rather than adding a second bespoke fetch/retry map. Connect a pool/body lookup Producer and an expected-key validating Consumer. Several subscribers can share a key; cancellation retains a fetch while any subscriber remains. [resolver API](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/resolver/src/lib.rs#L186-L224).

Use the existing authenticated Commonware P2P connection and logical-channel Sender/Receiver for the chosen tx announcement/admission bridge. Codec/crypto provide message encoding and signatures; runtime/actor provide mailbox/task ownership. The remaining wire bridge must make new transaction identities discoverable and connect valid bytes to the reused pool’s admission API. No reviewed standard service eliminates that application schema/inventory bridge, pool-level admission dedup, replay identity, retained-entry index or canonical cleanup. Buffered cache eviction is also not durable pool admission or transaction retirement. Broadcaster Feedback only confirms local acceptance for processing, not peer receipt. [Broadcaster boundary](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/broadcast/src/lib.rs#L14-L31).

The fit criterion is concrete: choose a pool backend whose transaction type, admission return, non-destructive/retained selection and canonical-outcome input can be adapted without imposing unadopted application semantics. Choose a transport stack whose security/session model matches the adopted validator network. Reuse standard services around that backend; do not describe the resulting application composition as a complete ready-made Commonware mempool.
