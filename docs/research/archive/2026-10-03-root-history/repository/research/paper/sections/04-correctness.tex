\section{Correctness and Liveness}
\label{sec:correctness}

\subsection{Safety Argument}

Safety begins with uniqueness of the execution input. Once existing consensus fixes the exact cut and cumulative ordered history, deterministic first-occurrence filtering and the prior consumed-ID history select the same transactions at every honest node. Each ID contributes at most one application attempt, including a failed attempt and its fee effects. A common canonical parent and identical runtime then determine one correct sequential result. Worker schedules and retry counts may differ, but state, statuses, events, and fees must agree. Validating input filtering and parallel execution remains P1/P2.

The initial placement profile assumes one authenticated map, permutation, and applicability context frozen for the experiment. Its producer-assignment predicate is part of block admission, not a local routing preference. For an admitted exact cut, execution correctness does not depend on whether the grouping heuristic predicted contention well. This does not make map validation optional or prove that online map changes preserve valid admission; those transition obligations remain D4.

The \(f+1\) result certificate relies on an honest witness for a unique canonical result. Under the configured eligibility policy \(\mathcal A_e(F)\), any \(f+1\) distinct authenticated epoch signers include an honest direct executor when at most f identities are faulty. If honest signers validate the full exact-context result, a false certificate cannot form. This argument is independent of native ordering-quorum size and does not replace ordering finality. PBFT supplies the matching-result precedent, not the unresolved Multimmit eligibility or checkpoint policy (M2). \citep{pbft}

Installing a certified canonical delta on its verified parent must yield the same final state as direct execution. Commitments bind the complete transferred data and outputs, not only a state root. Duplicate installation of the same cut is an idempotent no-op, while stale completion is rejected. An inductive installation rule checks parent continuity from genesis or a verified checkpoint through each cut. Different speculative roots alone are not evidence of Byzantine behavior.

\subsection{Conditional Liveness}

Result progress requires at least \(f+1\) honest eligible executors to receive the exact ordered range and parent, finish, and publish matching signatures. The eligibility policy must provide this despite withholding; an arbitrary fixed set of only \(f+1\) potential executors does not. If the entire epoch is eligible, native \(n-f\geq f+1\) supplies enough honest identities, but not execution or matching endpoint progress. A restricted policy needs its own argument. Checkpoint alignment and independent collection remain M2/D2; voting alone does not establish readiness.

Ordering does not wait for execution, but the pipeline needs bounded speculation and reserved capacity for finalized work to prevent backlog or candidate churn from starving certification. Progress additionally requires eventual synchrony, fair execution and data service, retention, and sufficient resources. For ingress-to-inclusion progress, the authorized producer must serve fairly or a safe authority-transfer protocol must be supplied; the frozen-map profile does not solve Byzantine-owner censorship. Optional sidecar preparation need not block cuts, but certificate checks and recovery consume resources. Activation after cut \(c+1\) guarantees neither all-node map delivery nor automatic recovery from a faulty producer.
