# Round 13: native event provenance and App interpretation

Source audited: `6233438985d8249d2b2bc1204191d5d405652288`, 2026-10-09. Current reader pages checked: consensus README/block-body/ordered-input, baton README/interfaces, and the native source layout map. No protocol changes or runtime claims.

## Result

Current docs correctly use native observations for optional candidate correlation and keep Marshal Update as the canonical App entry. A local pre-sign candidate cannot acquire signed provenance merely from its own successful verify; the later matching native observation can supply that provenance. Missing optional observations may forgo speculation, never canonical processing.

Two narrow wording improvements were identified. The owned consensus intro now says private AppExecutor dispatches **local** propose/verify jobs; remote chain-plane validation and Engine-open recovery have separate dispatch paths. Root received the same clarification for core/execution introductions and applied it. The core optional Activity table should say **native admission** instead of broadly implying every accepted artifact has an individually verified signature: native DA shares are deliberately admitted on structural checks before threshold recovery. This exception does not weaken transaction-header authentication.

## Exactly what transaction-header authentication covers

The verifier's ordinary batch includes a transaction_block_claim, which requires that the signer owns the header's producer chain and verifies the signature on that header (`scheme/bls12381_threshold/batch.rs:147`; `claims.rs:234–245`). A valid completion enters native readiness, then chain observation records producer ancestry and emits ValidatorCommand::Observe (`machine/reducer/dependencies.rs:515–545`; `machine/chain.rs:223–242`). Eligibility explicitly receives structurally valid, producer-authenticated headers. Its local custodied flag reuses the already completed pre-sign App check; other headers become Ready for App validation (`machine/eligibility.rs:214–252`).

Therefore a remote live verify request already has native producer-header provenance. Local custody verify occurs before signing, so a candidate whose report policy requires signed provenance must wait for an exact matching TransactionProposed or suitable signed TransactionBlock acceptance. Receiving a trusted BlockRef-only TransactionProposed can correlate to a retained header because that header's digest is part of BlockRef; it does not supply missing body data. App must still satisfy payload validity, durable custody, lifecycle, capacity and policy eligibility checks. No second native signature-verification layer is required for these local trusted observations.

The exception to a universal signature claim is intentional: `actors/verifier/verify.rs:92–119` runs only precheck_da_vote for incoming DA shares. `claims.rs:157–165` documents that omission. The recovered DA group certificate is checked, with individual attribution on failure (`assemble.rs:99–137`). An arbitrary ProtocolAccepted::DaVote is therefore not independently authenticated producer-header evidence and should not promote a candidate under a signed-header admission rule.

## Hints versus required Marshal wiring

This round does not repeat the queue/error analysis in round9-activity-pressure. The relevant provenance boundary is that optional **App observation** may be lossy; the supplied Marshal reporter must still receive the original native stream directly.

- TransactionProposed is ignored by Marshal. Accepted transaction headers, selected commitments, history openings and DA certificates help synchronization/backfill, but are not individually guaranteed to survive pressure.
- Marshal router overflow retains/coalesces the richest direct finality fact and accepted L-QC independently (`marshal/mailbox.rs:99–191`). Later synchronizer pressure may drop direct-finality hints while preserving L-QC synchronization (`marshal/actors/synchronizer/mailbox.rs:152–173`). Do not describe all native hints as either lossless or uniformly disposable.
- CertificateRecorded takes the dedicated per-chain coalescing release path (`marshal/mailbox.rs:500–520`); it carries a custody release, not canonical execution authority.
- Marshal's trusted local Update remains the canonical authority whether or not App observed verify, proposal, history, finality or certification hints first. Peer-supplied event-shaped values do not acquire that local authority.
