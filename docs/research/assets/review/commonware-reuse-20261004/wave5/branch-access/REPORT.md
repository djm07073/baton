# Wave 5: reuse keyed batch access before adding a rootless view engine

Baseline `b5747f6a28527a4507901f2e46b426b5ff2a4b7c`, following GitBook `VZgSSM1vxObvtUhGUVFR`; reviewer `/root/reuse_storage_types_v3`. Scope is fresh source/API inspection only. No canonical edits, external checkout changes, dependency changes, native compilation, protocol tests, schema/variant/sealing-policy selection or new public trait.

**Existing Any/Current drafts can serve ordinary root-deferred reads and writes. A separate generic view engine is not inherently required.** Native public fork creation still requires a sealed parent. For a rootless completed parent, a minimal *unadopted candidate* is to create separate existing batches at one valid applied/sealed anchor and replay retained exact-parent Storage-ready mutations into each before executing its child. This is an application effect/materialization adapter, not a new upstream fork primitive. If replayable effects are unavailable or invalid at that anchor, this path is unavailable; use an actually sealed valid parent or reexecute valid work.

## Three execution shapes without another database engine

1. **One continuing line:** retain/move one unsealed concrete draft across transactions or completed blocks. Its get observes prior write; hashing can remain deferred. This alone loses earlier owned draft boundaries as the handle advances. Retain exact prefix effects/outputs when partial commit or reconstruction may need them.
2. **Children of a sealed parent:** reuse `DatabaseSet::fork_batches(&sealed)` / `Merkleized::new_batch`. Existing native retained ancestors and read-through are enough. No application read-overlay implementation is required for this case.
3. **Children of a rootless parent (candidate):** keep application effects by exact execution prefix relative to a valid retained storage anchor. Make an independent upstream draft for each child from that same anchor; write the parent's already-converted keyed mutations into it, then execute the child using its existing get/write. The Executor still validates parent/input/runtime and controls work; Storage supplies valid access and later consumes selected work. This does not call fork on an unsealed parent and avoids cloning/extracting private native mutations.

Native Any's mutation map is private, `into_parts` is private, and `Base` is private. Neither Unmerkleized nor staged handle is Clone. There is no public root-deferred multi-child fork/retained-prefix extraction primitive in the inspected Any/Current/glue batch surfaces. `Db::new_batch` captures the currently applied commitment; the application cannot use it to rewind to an older state after sibling advancement. The private ancestor machinery and Any snapshot index are not a public historical snapshot API. [Raw pending fields](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/storage/src/qmdb/any/batch.rs#L263), [private parts and write](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/storage/src/qmdb/any/batch.rs#L1306), [sealed-parent fork](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/storage/src/qmdb/any/batch.rs#L2603), [applied-base capture](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/storage/src/qmdb/any/batch.rs#L2704).

**Replay is not arbitrary ChangeSet merging.** Mutation encoding may depend on the exact base; metadata, deletes, repeated writes and prefix normalization require a deterministic selected materialization rule. A flattened last-write-wins batch need not have the same operations root as separately sealed intermediate batches. Keep exact transaction outputs and direct execution evidence separately; storage-state equality does not prove execution-input equality. Choose no sealing frequency/root type here. Sibling DB advances require the existing invalidation/fencing/reexecution obligations, including during reads, stage/expand, materialization and hashing. [Branch applicability](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/storage/src/qmdb/batch_chain.rs#L188).

## Actual application examples

**Constantinople supplies a useful staged handoff shape.** Its `compute(StateBatch, transfers, strategy)` returns `(StateStaged, Option<StateUpdates>)`: an existing AnyStaged plus application indexed final values. A separate finalize_execution consumes those updates and merkleizes state/history concurrently. This concretely shows how Executor effects and Storage preparation can split without another batch representation. Its outer lifecycle nevertheless returns merkleized proposal/verify/apply state; do not import that dependency or force roots on every abandoned Baton attempt. Its aliases and update visibility are application-local, not new public Commonware traits. [Compute handoff](https://github.com/commonwarexyz/constantinople/blob/3b6c92e76bf582855615844a4175b8304808f6a9/crates/application/src/consensus/execution.rs#L160), [exact types/finalizer](https://github.com/commonwarexyz/constantinople/blob/3b6c92e76bf582855615844a4175b8304808f6a9/crates/application/src/consensus/db.rs#L57).

**Kora shows effects and an application overlay, with different storage semantics.** Its BlockExecutor returns ExecutionOutcome containing ChangeSet and receipts; StoreBatches is three application Vec mutation lists. OverlayState<S> retains Arc<ChangeSet> and reads overrides before base; it is EVM account/code/storage semantics, not an upstream rootless QMDB tree or immutable historical snapshot. QmdbStore::build_batches reads current account generation to encode new keys, demonstrating why effect conversion must be bound to the correct base. Its QmdbHandle comment “commit changes atomically” does not establish disk crash atomicity: apply_batches writes three partitions sequentially and uses sentinel sequence markers to detect partial commits. Do not import that comment as a state/output/cursor transaction guarantee. [Execution result](https://github.com/refcell/kora/blob/446b4c7aba80e8358486ddb43a276c5bfa183102/crates/node/executor/src/outcome.rs#L9), [overlay](https://github.com/refcell/kora/blob/446b4c7aba80e8358486ddb43a276c5bfa183102/crates/storage/overlay/src/overlay.rs#L7), [base-dependent conversion](https://github.com/refcell/kora/blob/446b4c7aba80e8358486ddb43a276c5bfa183102/crates/storage/qmdb/src/store.rs#L266), [sequential partition writes](https://github.com/refcell/kora/blob/446b4c7aba80e8358486ddb43a276c5bfa183102/crates/storage/qmdb/src/store.rs#L334).
