# Round 14: production extension surface inventory

Source: `6233438985d8249d2b2bc1204191d5d405652288`, 2026-10-09. This independently checks the public export boundary and plausible overlooked seams; round8-native-policy-gap contains the detailed native construction/signing/recovery chain. No new hook, codec, implementation or protocol proof is adopted here.

## Finding

No existing production extension accepts an App-selected cross-lane prefix for the actual native leader proposal, validates its adoption before native votes, and makes Marshal recover that frozen interpretation. The current gap is real **for that full-Baton contract**. App-owned TxPool, speculative scheduling, execution, result handling and canonical application remain implementable through the existing callbacks and Marshal APIs without new public App traits.

This is not a claim that arbitrary application protocols cannot be built atop an ordered payload stream, or that native data cannot coincidentally produce a preferred order. An App can define richer body semantics. Such a reinterpretation does not make the existing Engine/Marshal authenticate and deliver a selected prefix of the existing producer blocks under the documented native contract.

## Additional seams challenged in this round

**Custom LqcVerifier.** This is a real public trait, but its only input is an externally resolved Lqc and its output is success/failure (`marshal/types.rs:41–51`). Service uses it for peer backfill and live floor anchors (`actors/backfill/actor.rs:489–511`; `actors/synchronizer/floor.rs:94`). Trusted native ProtocolAccepted::Lqc goes through router catalog staging/trigger without this verifier (`service/router.rs:249–265`). Adding a private policy check here neither changes Engine's pre-vote rule nor covers all local finality, and cannot select a different traversal. Rejecting native-finalized proofs later can stop consumption; it does not establish protected-prefix adoption. Reuse the supplied SchemeVerifier for the existing contract.

**State-sync floors and output bounds.** Start::Floor and install_floor choose an authenticated native stream boundary, with the lifecycle distinctions audited in round11. They do not carry arbitrary App order or a policy interpreter. Floor's anchor/history/emitted frontier and generation coordinate recovery of the fixed native stream. max_commit_outputs and max_pending_acks bound chunks/windowing; they do not reorder membership within the output sequence. Treating a preferred order as an invented floor would violate the existing proof/frontier checks or change caller trust, not use an ordering extension.

**Constructors and feature-gated signing.** LeaderBlock::new is public, but the object contains only round, parent, history and positional per-chain proposals. The constructor checks proposal i belongs to chain i (`types/block.rs:802–844`); canonical encoding writes precisely those fields (`:955–981`). Native construction invokes it with the selected parent and that parent's child_history (`machine/view/proposal.rs:304–352`). Normal build sign_leader_block is crate-private: mocks_pub exposes it only with test/mocks (`scheme/bls12381_threshold/mod.rs:24–36`; `sign.rs:51–61`). Even enabling mocks only allows fixture/direct-signing access; it does not add an Engine policy hook or recovery-safe authorization path. Public private-key construction likewise does not make bypassing the native signing reservation a supported extension.

**Transport, body semantics and scheduling.** Sender/Receiver/Resolver implementations, Relay and App payload construction can affect which data is available and when. App can include metadata in a body or execute a richer application protocol. Current leader validation and Marshal ordering do not inspect that metadata as a selected cross-lane prefix. A transport filter or delayed verify cannot turn an App policy into authenticated native cut semantics, and optional observer feedback is not a vote. None of these mechanisms warrants another App BlockService/Executor/Orderer interface.

## Fixed traversal and continuation rechecked

Marshal's protocol module is private; SlotStream and FinalSweep are crate-private (`marshal/mod.rs:71`; `protocol/order.rs:363,416`). SlotStream runs the two fixed native passes; FinalSweep's halt defers later slots when a proposed tip falls short or extension is unsettled (`order.rs:409–463`). History synchronization reconstructs the same stream from oldest-first authenticated openings (`actors/synchronizer/history.rs:34–49`), and direct finality uses a fact only when it matches the floor proof's exact round/leader/parent (`:118–153`). A subsequent proof/history opening continues native interpretation; no user-supplied closure determines the continuation.

Thus the supported selection knob remains per-chain suffix inclusion in propose_chain (`machine/vote_body.rs:119–159`). It can change native pass boundaries through proposed heights, but cannot guarantee an arbitrary selected cross-lane prefix. The additional Baton preservation/adoption/availability proof remains open; this audit does not imply one new field or callback would suffice.
