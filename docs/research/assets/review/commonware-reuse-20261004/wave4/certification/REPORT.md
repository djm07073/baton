No dependency change, scheme selection, executable adapter, native protocol compilation or protocol tests. The source manifest records Git blob matches for every inspected file. ## Finding

Current Executor docs reuse only `Signer` / `Verifier` for execution certificates. Commonware already provides protocol-independent certificate building blocks. Reuse those where the selected result-signing scheme fits, rather than implementing signature batching, signer-bitmaps or cryptographic aggregation again. Executor still owns the full execution statement, trusted epoch roster, per-subject collection, direct-execution signing authority and irrevocable input/base checks.

| Existing API | Reusable work | Application connection |
|---|---|---|
| `certificate::Subject` / `Namespace` | Signing namespace and message construction surface | Encode the entire exact result statement; define an execution-result domain independent of native votes |
| `certificate::Attestation<S>` | Indexed signer and scheme signature, with existing codec | Associate it with the exact full subject and authenticated epoch roster; the attestation itself contains no result subject |
| `certificate::Scheme::{sign, verify_attestation, verify_attestations}` | Cryptographic signing and individual/batch verification | Gate signing on own direct execution and prepared root; deduplicate candidates before batch verification |
| `Scheme::assemble` / `certificate::Verifier::verify_certificate` | Scheme-specific certificate construction and cryptographic checking | Configure an execution-result threshold consistently on both sides, and retain full application verification |
| `certificate::Signers`, `Participant`, ordered roster | Existing bounded signer encoding and deterministic indexing | Bind indices to the exact eligible epoch roster; validate and deduplicate untrusted indices before construction |
| `N5f1::f_plus_one(n)` | Existing `f+1` arithmetic for the adopted committee model | Use the same authenticated full epoch roster/fault budget; do not count a partial responders roster |

## Exact threshold and collection boundaries

1. `ordered::Quorum` delegates to `Faults::quorum`. The built-in `N5f1` uses the default `n - max_faults(n)`, hence `4f+1` for `n=5f+1`. Passing `N5f1` unchanged to a generic result-certificate wrapper would introduce the wrong execution threshold. `N3f1` is also not the result threshold. A protocol-specific result scheme/quorum adapter is a possible seam, not an adopted fault-model change. Lower-level signature/batch/bitmap primitives remain reusable while the concrete result scheme is open.
2. `assemble` assumes supplied attestations have already been verified for one full subject; Ed25519 and BLS multisig implementations check indices/count and encode/aggregate signatures but do not authenticate each signature or establish same-subject equality. Batch verification and assembly must receive only distinct, valid signer candidates. The public trait explicitly declares duplicate input undefined; `Signers::from` panics on duplicates/out-of-range indices. Untrusted ingress must not be passed straight to it.
3. The attestation wire type contains only signer index and signature. The certificate contains signer representation and signature data, not the execution statement. A versioned, bounded application envelope still needs the statement or an unambiguous exact-subject reference. Full result/input/runtime/base/output binding is not supplied by the crypto codec.
4. A certificate decode configuration bounds participant storage; exact roster length and actual keys are enforced by certificate verification. Network ingress must use the authenticated roster-bound codec configuration, not `certificate_codec_config_unbounded`, which upstream restricts to trusted local storage.
5. Reuse a retained map keyed by the full result subject for incremental distinct eligible signatures. This is Executor application state, not a new generic collector engine. `collector::p2p` remains a conditional pull-attestation transport; its response count and seen-peer lifecycle do not replace verified `f+1` counting.

## Scheme choices remain open

Ed25519 certificates retain individual signatures and use existing batch verification with invalid-signature isolation. BLS multisig certificates retain signer indices while aggregating signatures, but caller-verified proof of possession for every signing key is a constructor prerequisite: the public Generic constructor does not perform that verification. Threshold BLS is explicitly non-attributable; do not assume its certificate proves the currently required original signer identities. Any alternate evidence/setup contract requires deliberate design rather than substituting the native DA sharing setup. None of these findings chooses keys, a scheme, a certificate wire format or a signing boundary for Baton.
