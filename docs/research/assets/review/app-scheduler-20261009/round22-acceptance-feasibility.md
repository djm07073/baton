## Adopted cases and source feasibility

- **Local versus remote versus recovery verify:** local false/closure stops the voter (`actors/voter/tests/production.rs:337` and actor/live.rs:578–601); remote closure becomes Unavailable and reschedules (`chain_plane.rs:528–550`, eligibility.rs:352–355, existing test :798); recovery requires Ok(true), supports bounded concurrent gates and fails even with another sibling pending (`storage/recovery.rs:670–758`). App tests must preserve the distinct verdict and request lifetimes. The existing verify-admission row covers them; it now explicitly requires recovery callbacks to be serviced before Engine::open returns, preventing a ready-first startup deadlock.
- **Canonical-first input:** Validator live planes are absent for Observer (`actor/chains.rs:114–129`), while Marshal delivery passes complete Update directly to its Reporter (`delivery/actor.rs:303–327`). Existing fixtures can drive real delivery without invoking App Automaton first. The canonical row now explicitly says no prior verify or speculative admission, including Observer. The test still needs the real App to validate/execute/import/apply that first input.
- **Zero reports:** the previous round restored the adopted actual-parent-valid base fallback before protected adoption. The selection row already names it. This is an App/Baton assertion, not something a native Marshal fixture proves; no native report window or selection hook is claimed.
- **Cancellation versus worker termination:** runtime Handle/AbortOnDrop documentation distinguishes dropping a wait from stopping spawned or completion work (`runtime/utils/handle.rs:358–374`); Pool::cancel_all only clears held futures (`utils/futures.rs:61–67`). The one-worker acceptance row correctly waits for safe ownership/resource release and treats a normal VM revert as a completed outcome. Native canceled-custody tests support request fencing, not physical termination of arbitrary App workers.
- **Progress within the ACK window:** delivery stops reporting when pending queue length reaches max, independent of the existence of additional committed outputs (`delivery/actor.rs:237–247`, acks.rs:74–96`). If App waits for window+1 inputs before its first durable application/ACK, no later input can arrive. Added this explicit batching/signing-range acceptance condition to Delivery capacity, preserving execution/interfaces.md's existing rule. A larger signing range remains allowed when durable apply/ACK progresses independently; no per-block signing policy was added.
- **App ACK versus native cursor I/O:** Exact ACK retirement frees the ordinary window before cursor sync completes; later cursor persistence is another recoverable milestone (`acks.rs:1–5,105–121`). Pausing App storage and pausing cursor storage are distinct tests. Existing ACK/recovery and scheduling-independence rows already require these boundaries and progress under optional backlog, so no additional row is needed.
