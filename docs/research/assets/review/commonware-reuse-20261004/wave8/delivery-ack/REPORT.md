# Wave 8 — reuse local acknowledgement handles, keep durable range semantics

Root source audit against freshly fetched pinned native/release/Tempo files. Scope is documentation and public API fit; no native compilation, protocol implementation or new default transport/cursor design.

## Public reusable mechanism

Native publicly exports `Acknowledgement`; its `handle() -> (Self, Self::Waiter)` and consuming `acknowledge(self)` cover local completion notification. `Exact::handle()` returns an Exact handle and ExactWaiter. ExactWaiter is a future of `Result<(), Canceled>`. Native and inspected registry-release source are byte-identical. The Commonware MCP explicitly corroborates v2026.9.0: all 82 numbered zero-based lines match the fresh release blob. [Trait](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/utils/src/acknowledgement.rs#L24), [Export](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/utils/src/lib.rs#L207), [Exact implementation](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/utils/src/acknowledgement.rs#L100).

Exact is all-held-instances completion, not a quorum. Cloning increments the remaining count. Every instance must be consumed by acknowledge; dropping any unacknowledged instance permanently cancels the waiter. Dropping only the waiter does not cancel handles. None of these handles carries input identity, CommitResult, f+1 signatures, durable metadata, a wire codec, a timeout or restart replay. Therefore it cannot replace the rich adopted receipt or state/result verification. [Clone/drop](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/utils/src/acknowledgement.rs#L55), [Waiter](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/utils/src/acknowledgement.rs#L137).

For the chosen local delivery model, Orderer can associate an existing Exact/oneshot notification with the same immutable OrderedRange and signal only after verifying its durable CommitResult. Handle/future plumbing does not justify another ACK engine or public trait. No change to the adopted `Orderer::acknowledge(range, result)` signature is required. This is an optional internal attachment recipe, not a requirement to add an extra waiter. In particular, cloning mandatory Exact acknowledgement to optional Baton telemetry would incorrectly let that observer block delivery. Existing optional Baton notification stays outside this local receipt predicate.

## Actual Tempo assembly and limits

Tempo's executor Mailbox implements Reporter of Marshal Update<Block>, forwarding into its existing mailbox. Update::Block carries an Exact handle. The executor stores it with the block in FinalizedBlockRequest, queues it through execution/forkchoice work, then consumes it when the tracked finalized state covers that block. This is concrete existing attachment composition, not a named generic ResultService. [Mailbox](https://github.com/tempoxyz/tempo/blob/61c979a524f9af5de9c540a0088c429a44741e4c/crates/consensus/src/executor/ingress.rs#L201), [Receipt holder](https://github.com/tempoxyz/tempo/blob/61c979a524f9af5de9c540a0088c429a44741e4c/crates/consensus/src/executor/actor.rs#L1751), [Completion](https://github.com/tempoxyz/tempo/blob/61c979a524f9af5de9c540a0088c429a44741e4c/crates/consensus/src/executor/actor.rs#L1010).

The inspected Simplex Marshal creates an acknowledgement pair at application delivery, stores its waiter with exact height/commitment and handles it in FIFO order. Its PendingAck/PendingAcks structs are private (`pub(super)`), so an external native Multimmit attachment cannot import that tracker unchanged. It is an ownership/identity pattern around the public handle. [Private tracker](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/consensus/src/marshal/core/acks.rs#L15), [Dispatch](https://github.com/commonwarexyz/monorepo/blob/d476a2361ce6840d2b9d0aa6fb30a924429046d4/consensus/src/marshal/core/actor.rs#L1894).

Marshal dispatch itself waits for archive durability, while its processed-height update initially buffers metadata and needs separate sync. Tempo's predicate relies on its engine/forkchoice/canonical history, including a restart case where the EL finalized marker lags; copying numeric-height completion alone is not a Baton durable-range proof. Baton instead keeps exact input/base/runtime/order/output/cursor/provenance linkage under current Storage/Executor ownership. [Buffered processed height](https://github.com/commonwarexyz/monorepo/blob/d476a2361ce6840d2b9d0aa6fb30a924429046d4/consensus/src/marshal/core/actor.rs#L2366).

## Minimal reader change

Only a short paragraph in ordered-input's storage/replay section is justified: local Exact/oneshot completion reuse, associated immutable range/full durable receipt, clone/drop/cancellation boundary, private Simplex tracker not a drop-in, no optional observer approval. Existing cursor/recovery/retention paragraphs remain authoritative. No body ACK, report wait, direction ACK, native cut wait, quorum/backend/schema/budget or actor count changes are proposed.
