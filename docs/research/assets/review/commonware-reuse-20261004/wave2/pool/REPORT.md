Neither improvement selects a backend, workload, filtering placement or transaction semantics.

## 1. Constantinople reuse is substantial but requires source adaptation

The existing pool is a real actor with bounded mailbox admission, two queue lanes, local digest dedup, transaction byte accounting, whole-entry selection and proposal/status correlation. Reusing those pieces can avoid writing another queue or packing kernel. The following boundaries are observable in source and correctly reflected in the current Tx pages:

| Source surface | Verified behavior | Baton connection |
|---|---|---|
| `TransactionSource::propose` | Concrete `Header`, consensus `Round`, `filled`, returns fixed `VerifiedTransaction`; trait also requires marshal `Update<SealedBlock>` Reporter | Native producer-context conversion and durable execution outcome conversion are application work |
| `Mailbox::channel`, `Actor::new/start` | Public entry points; actor startup receives an HTTP listener | Importable source-level actor surface, not generic peer transaction gossip |
| `Mailbox::try_submit` | Public; bounded enqueue returns a receiver resolving terminal batch status | Cannot implement admission by awaiting this receiver; local enqueue is also not final accepted admission |
| `Mailbox::try_ingest` | Existing accepted/dropped admission-result path, but `pub(super)` | Expose/adapt the existing path rather than inventing a second queue owner |
| `PoolLane`, `PoolEntry`, `new_transactions`, `total_bytes_for`, `can_admit_submission`, `pop_proposal` | Private structs/functions in actor implementation | Kernel extraction/generalization is new integration work; they are not public generic imports |
| `pop_lane_proposal` | Pops entries, subtracts queue bytes, retains only proposed digests/height in status bookkeeping | Retained bytes, cancellation/reselection and outstanding-material budgets must be reconciled |
| `Update::Block` handler | Inspects reported bodies only when local `proposed` is nonempty; resolves those proposed digests or expires them by height/grace | Does not globally clean peer-included queued transactions or prove durable Baton execution outcomes |

Primary sources: [TransactionSource](https://github.com/commonwarexyz/constantinople/blob/3b6c92e76bf582855615844a4175b8304808f6a9/crates/mempool/src/lib.rs#L9-L34), [mailbox visibility/completion](https://github.com/commonwarexyz/constantinople/blob/3b6c92e76bf582855615844a4175b8304808f6a9/crates/mempool/src/webserver/mailbox.rs#L102-L174), [destructive selection](https://github.com/commonwarexyz/constantinople/blob/3b6c92e76bf582855615844a4175b8304808f6a9/crates/mempool/src/webserver/actor.rs#L402-L457), [dedup/budgets](https://github.com/commonwarexyz/constantinople/blob/3b6c92e76bf582855615844a4175b8304808f6a9/crates/mempool/src/webserver/actor.rs#L559-L622), [local outstanding status handler](https://github.com/commonwarexyz/constantinople/blob/3b6c92e76bf582855615844a4175b8304808f6a9/crates/mempool/src/webserver/actor.rs#L844-L896).

**Additional import qualification:** the package has `publish = false`; this is source/Git-workspace reuse, not a claim of an available published generic crate. Its workspace Commonware revision is `92036f4beefedc9817f0954d98fb99e0b52431cb`, distinct from Baton’s native pin. Its fixed transaction includes sender, recipient, transfer value and nonce, and package dependencies include Constantinople primitives, Axum/Tokio/reqwest and Commonware. Passing different generic hash/key parameters does not generalize the transaction semantics. [Package declaration/dependencies](https://github.com/commonwarexyz/constantinople/blob/3b6c92e76bf582855615844a4175b8304808f6a9/crates/mempool/Cargo.toml#L1-L44), [workspace pins](https://github.com/commonwarexyz/constantinople/blob/3b6c92e76bf582855615844a4175b8304808f6a9/Cargo.toml#L51-L67), [transaction representation](https://github.com/commonwarexyz/constantinople/blob/3b6c92e76bf582855615844a4175b8304808f6a9/crates/primitives/src/transaction.rs#L134-L164).

### Untrusted submission and identity alignment

`VerifiedTransaction` is exactly an alias of `SignedTransaction`; `new_unchecked` is public. `try_submit` accepts `batch_id`, `digests` and transactions separately. The actor dedups using each transaction's `message_digest` but registers watchers from the separate supplied digest vector. A bridge must validate the selected signing subject, recompute its chosen identifiers and align the status/watcher digests with actual admitted transactions. A name or caller-supplied digest list is not verification. [Alias/construction](https://github.com/commonwarexyz/constantinople/blob/3b6c92e76bf582855615844a4175b8304808f6a9/crates/primitives/src/transaction.rs#L41-L54), [separate mailbox arguments](https://github.com/commonwarexyz/constantinople/blob/3b6c92e76bf582855615844a4175b8304808f6a9/crates/mempool/src/webserver/mailbox.rs#L112-L139), [dedup versus watcher input](https://github.com/commonwarexyz/constantinople/blob/3b6c92e76bf582855615844a4175b8304808f6a9/crates/mempool/src/webserver/actor.rs#L747-L796).

The HTTP path does real work before mailbox submission: bounded request/decode counts, signed-transaction byte limit, bounded verification job ownership, signature-check helper invocation with namespace, and derivation of digests from resulting transactions. That is the validation path a bypassing P2P adapter must preserve/adapt, not evidence that the mailbox performs it. The HTTP relayer fans out requests; it is not a generic authenticated Commonware tx gossip service. [HTTP verification](https://github.com/commonwarexyz/constantinople/blob/3b6c92e76bf582855615844a4175b8304808f6a9/crates/mempool/src/webserver/http.rs#L246-L334), [relayer](https://github.com/commonwarexyz/constantinople/blob/3b6c92e76bf582855615844a4175b8304808f6a9/bin/validator/src/relayer.rs#L455).

## 2. Tempo/Reth is an actual complete assembly with explicit backend bounds

Tempo constructs `TransactionValidationTaskExecutor::eth_builder` from provider/EVM configuration, builds Reth `Pool::new`, wraps it with the Tempo 2D nonce pool, starts base maintenance tasks and its extra canonical maintenance task. Its network builder calls `ctx.start_network(network, pool)` on the standard Ethereum network and optionally installs a separate certificate RLPx subprotocol. The pool is not carried by the Commonware body broadcast channel. [Pool construction](https://github.com/tempoxyz/tempo/blob/61c979a524f9af5de9c540a0088c429a44741e4c/crates/node/src/node.rs#L772-L856), [transaction network](https://github.com/tempoxyz/tempo/blob/61c979a524f9af5de9c540a0088c429a44741e4c/crates/node/src/node.rs#L180-L231).

Reth's TransactionsManager owns announcements, unknown-hash fetch/import, per-peer state and propagation with Ethereum wire/network types. This is strong reuse evidence for the complete EVM-compatible stack, not merely a local queue. It is not a generic opaque tx protocol that can be placed on Commonware Sender/Receiver unchanged. [Manager responsibilities/types](https://github.com/paradigmxyz/reth/blob/038edab20dfff017f7a7502e683c732e5628ad89/crates/net/network/src/transactions/mod.rs#L271-L338).

The bounds are explicit: `TransactionPool::Transaction: EthPoolTransaction`, `PoolTransaction` extends Alloy transaction and associates signed consensus/pooled forms; pool assumptions include account nonces, gas and fees. Tempo adds EVM/provider/precompile/keychain/AMM/AA requirements. Preserve base-Reth-first conditional reuse rather than adopting Tempo application extensions merely because its consensus is Commonware-based. [Reth assumptions](https://github.com/paradigmxyz/reth/blob/038edab20dfff017f7a7502e683c732e5628ad89/crates/transaction-pool/src/lib.rs#L136-L161), [trait bounds](https://github.com/paradigmxyz/reth/blob/038edab20dfff017f7a7502e683c732e5628ad89/crates/transaction-pool/src/traits.rs#L114-L116), [transaction associated forms](https://github.com/paradigmxyz/reth/blob/038edab20dfff017f7a7502e683c732e5628ad89/crates/transaction-pool/src/traits.rs#L1340-L1350), [Tempo dependencies](https://github.com/tempoxyz/tempo/blob/61c979a524f9af5de9c540a0088c429a44741e4c/crates/transaction-pool/Cargo.toml#L20-L45).

Its builder is execution-aware: pool best-transaction iteration, gas and full RLP encoded-body accounting, EVM execution and returned executed payload. The Commonware application subscribes to an Executor-owned proposal build; canceled subscriber ownership is a useful integration pattern. These are not an adopted native Multimmit execution-parent or custody contract. `mark_invalid` at capacity exclusions is iterator dependency exclusion, not proof of permanent application invalidity or canonical retirement. [Builder capacity handling](https://github.com/tempoxyz/tempo/blob/61c979a524f9af5de9c540a0088c429a44741e4c/crates/payload/builder/src/lib.rs#L573-L633), [execution](https://github.com/tempoxyz/tempo/blob/61c979a524f9af5de9c540a0088c429a44741e4c/crates/payload/builder/src/lib.rs#L650-L711), [proposal ownership](https://github.com/tempoxyz/tempo/blob/61c979a524f9af5de9c540a0088c429a44741e4c/crates/consensus/src/consensus/application/impl.rs#L205-L237).

### Positive reuse addition: mined pruning and full canonical maintenance

The current Tx page correctly warns that `remove_transactions` is discarded removal. The same pinned Reth has **`prune_transaction` and `prune_transactions`**, with explicitly mined semantics: descendants stay eligible rather than being parked behind a nonce gap. These APIs are already implemented, not a proposed Baton replacement. Tempo's hybrid pool implements `prune_transactions` by removing from its AA pool and calling the protocol pool's mined prune path. [Reth mined-pruning API](https://github.com/paradigmxyz/reth/blob/038edab20dfff017f7a7502e683c732e5628ad89/crates/transaction-pool/src/traits.rs#L524-L560), [implementation](https://github.com/paradigmxyz/reth/blob/038edab20dfff017f7a7502e683c732e5628ad89/crates/transaction-pool/src/pool/mod.rs#L1138-L1152), [Tempo implementation](https://github.com/tempoxyz/tempo/blob/61c979a524f9af5de9c540a0088c429a44741e4c/crates/transaction-pool/src/tempo_pool.rs#L1027-L1034).

Full canonical maintenance uses **`TransactionPoolExt::on_canonical_state_change(CanonicalStateUpdate)`** and account updates. CanonicalStateUpdate includes a sealed new tip, pending base/blob fees, changed accounts, mined transaction hashes and update kind; its documented range must extend the pool's known canonical tip. The implementation updates validator head, accounts, mined entries and listeners. `prune_transactions` alone is not this complete fee/provider/account refresh. [Canonical API](https://github.com/paradigmxyz/reth/blob/038edab20dfff017f7a7502e683c732e5628ad89/crates/transaction-pool/src/traits.rs#L773-L805), [update representation and ancestry](https://github.com/paradigmxyz/reth/blob/038edab20dfff017f7a7502e683c732e5628ad89/crates/transaction-pool/src/traits.rs#L1030-L1055), [canonical implementation](https://github.com/paradigmxyz/reth/blob/038edab20dfff017f7a7502e683c732e5628ad89/crates/transaction-pool/src/pool/mod.rs#L531-L575).

Recommended narrow addition to Tx reuse prose: if an Ethereum-compatible backend is later selected, assess these existing canonical/mined APIs for durable Executor outcome mapping instead of recreating removal/promotion machinery. The adapter still supplies actual canonical state and preserves Baton irrevocability; it cannot infer success from producer-lane inclusion or import Reth reorg behavior as a Baton rule. Tempo maintenance actually subscribes to canonical Commit/Reorg notifications and post-state, and deliberately excludes mined txs from discard scans. [Tempo canonical maintenance](https://github.com/tempoxyz/tempo/blob/61c979a524f9af5de9c540a0088c429a44741e4c/crates/transaction-pool/src/maintain.rs#L475-L548).

## 3. Commonware buffer/resolver replaces machinery, not semantic pool policy

The native pinned `buffered::Mailbox::{broadcast_shared,get,subscribe}` signatures match the current body and Rust-interface recipe. Broadcast uses Recipients and Arc payload; get/subscribe require a known digest. The buffer has no admission stream yielding every unknown tx to TxPool and does not establish durable custody or semantic/canonical replay suppression. [Mailbox](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/broadcast/src/buffered/ingress.rs#L89-L143), [cache purpose](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/broadcast/src/buffered/mod.rs#L1-L23).

The native Resolver trait exposes fetch/fetch_all/retain, with subscribers keyed to a peer-visible request. Producer serves retained bytes; Consumer validates delivery against expected key/context and communicates outcome. These primitives already supply keyed fetching/correlation/retry/cancellation. Inventory, tx identity, admission validation, candidate retention and canonical outcomes remain application/backend contracts. Local scheduling Feedback must not be called peer receipt. The current documents make these distinctions and do not need a second generic cache/fetch engine. [Resolver contracts](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/resolver/src/lib.rs#L136-L224), [generic P2P engine](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/resolver/src/p2p/engine.rs#L36).

Tempo actually constructs and starts a Commonware buffered body engine and connects its mailbox/resolver to consensus assembly. That supports the documented body composition. Its transaction transport remains the Reth network above, and its Marshal assembly does not itself demonstrate a native Multimmit adapter. The current body page's explicit warning against unchanged Marshal reuse is necessary. [Body buffer construction](https://github.com/tempoxyz/tempo/blob/61c979a524f9af5de9c540a0088c429a44741e4c/crates/consensus/src/consensus/engine.rs#L207-L231), [body startup](https://github.com/tempoxyz/tempo/blob/61c979a524f9af5de9c540a0088c429a44741e4c/crates/consensus/src/consensus/engine.rs#L526-L539).
