# Wave 5: exact body archive and resolver attachment

**Commonware already supplies body-value storage, digest/index lookup, covering sync, gap enumeration, and request/retry transport. The missing connection is a narrow application binding between authenticated native headers/context and retained bytes, with one owner coordinating consuming archive mutations and borrowed queries. Another generic body storage/fetch actor is unnecessary.**

## 1. Existing exact storage operations

Signatures below abbreviate `impl Future<Output = ...> + Send` as `async`; they are existing upstream APIs, not new Baton traits.

| Native public API | Exact shape / behavior | Narrow attachment responsibility |
|---|---|---|
| `archive::Archive` | `Key: Array`, `Value: Codec + Send`; `put(self, index: u64, key, value) -> Result<Self, Error>` | Allocate/bind an index according to the still-open application schema; ordinary put ignores an occupied index |
| `Archive::get`, `has` | `get(&self, Identifier<'_, Key>) -> Result<Option<Value>, Error>`; `has(...) -> Result<bool, Error>` | `Identifier::Index(u64)` and `Identifier::Key(&K)` are alternative lookups, not an authenticated header/context join |
| `immutable::Archive<E,K,V>` | Public `init`; `E: BufferPooler + Storage + Metrics + Clock`, `K: Array`, `V: CodecShared`; implements `Archive` | Unique logical indices and permanent retention; no `MultiArchive` implementation at this pin |
| `prunable::Archive<T,E,K,V>` | Same value/key bounds, `T: Translator`; public `init`, consuming `prune(self, min: u64)`; implements `Archive` and `MultiArchive` | Section-rounded release only when application custody/serving/recovery references permit it |
| `MultiArchive::put_multi`, `get_all` | `put_multi(self,index,key,value) -> Result<Self,Error>`; `get_all(&self,index) -> Result<Option<Vec<Value>>,Error>` | Supports overlapping indices; `get(Index)` returns the first stored value; `get_all` has no maximum argument |

`Array` extends `Span` with fixed encoding and byte access. Resolver's key is only `Span`, whose codec config is `()`. A digest can serve both roles, but a composite resolver request key cannot be assumed to be an archive `Array`; a chosen wire-key/schema mapping may translate between them. No encoding format is adopted here. [Key requirements](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/utils/src/sequence/mod.rs#L37).

Both concrete archives expose borrowed asynchronous `get` over a boxed inner store and consuming writer operations. Neither source exposes a Clone/read-only handle or a separate public shared-reader constructor. An application can coordinate queries/writes under its existing attachment owner; it must not describe cloning the archive as an upstream read handle. This does not require a new public body trait or actor.

### Exact lookup is a schema binding, not another lookup engine

Native `TransactionBlockHeader` contains epoch, producer chain, chain-local height, parent **header** digest and body commitment. Its protocol ID hashes the complete header. `Context` reproduces epoch/chain/height/parent, while the payload digest is supplied separately to callbacks. Thus the minimal application join is:

`authenticated header ID -> exact header/context + body commitment -> retained body bytes`

and required parent lookup follows `header.parent()` to the parent header, then that header's commitment to its bytes. A producer-lane height alone is neither a global archive index nor a fork identity. Archive does not authenticate this relationship or provide an ancestry interpretation. Existing header/native evidence storage can supply the header record; an extra generic ancestry database is not implied. [Native context](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/consensus/src/multimmit/types/block.rs#L47), [native header identities](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/consensus/src/multimmit/types/block.rs#L119).

Archive's same key may occur at multiple indices and a key lookup may return **any** associated value. A digest-only lookup therefore cannot select among different context-dependent envelopes stored under that same digest. Viable schema families include stable content records selected by commitment plus a separate authenticated header/context binding, or uniquely addressed complete records with verified context. These are alternatives, not a selected layout. MultiArchive permits index overlap but does not remove key ambiguity. Its `has_at` can verify a chosen index/key relation; the application still checks expected bytes and header/parent context. [Key ambiguity](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/storage/src/archive/mod.rs#L1).

Prunable's translated-key index already checks full stored keys before returning a value or presence result, including `has_at`. Its translator collisions need no custom collision-validation index. Full-key presence nevertheless does not recompute the application's body commitment. `get_all` materializes all values at the index, so it is not intrinsically a bounded response operation. Its admission/serving budget remains an application decision. [Full-key lookup](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/storage/src/archive/prunable/storage.rs#L276), [get_all and has_at](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/storage/src/archive/prunable/storage.rs#L525).

### Physical locations and sync handles

At this native pin Archive exposes no physical `Location` lookup: its identifier is index/key. The lower Freezer exports `Cursor`, returned by `put`, and `freezer::Identifier::Cursor(Cursor)` for direct value access. Cursor is a physical section/offset/size locator; direct cursor reads bypass the full-key lookup. It is not an authenticated header ID or context binding. Existing immutable Archive already composes Freezer, Ordinal and committed metadata, so applications need not recreate that physical mapping/recovery layer merely to fetch bodies. [Freezer identifier](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/storage/src/freezer/mod.rs#L217), [Cursor](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/storage/src/freezer/storage.rs#L24), [cursor read](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/storage/src/freezer/storage.rs#L899), [immutable ordinal composition](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/storage/src/archive/immutable/storage.rs#L89).

Direct Freezer `put` updates the key's latest value and returns `(Self,Cursor)`; `sync` returns `(Self,Checkpoint)`. Direct `init(None)` or an empty checkpoint deletes existing freezer data. Immutable Archive handles the checkpoint publication itself: freezer and ordinal sync precede committed metadata; restart uses that metadata. Prefer the existing composed Archive when that workload fits rather than rebuilding checkpoint management around raw Freezer. This is a reuse observation, not a selected body backend. [Freezer methods](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/storage/src/freezer/storage.rs#L1151), [immutable recovery](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/storage/src/archive/immutable/mod.rs#L19).

Immutable uses Archive's default `start_sync`: complete synchronous sync first, then return an already-finished handle. Prunable overrides it with in-flight section sync; its `requested` set preserves covering outstanding work. Later writes need their own covering completion. Pruning removes section data and associated pending/requested work; a prior sync success is not permission to release retained bytes. Below-floor combined puts may return successfully with no stored data. These details refine the existing reader custody caveat without imposing another barrier. [Default completion](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/storage/src/archive/mod.rs#L137), [prunable sync](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/storage/src/archive/prunable/storage.rs#L462), [pruning](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/storage/src/archive/prunable/storage.rs#L401), [combined puts](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/storage/src/archive/prunable/storage.rs#L629).

## 2. Minimal resolver handle connection

Existing `p2p::Producer: Clone + Send + 'static` has `Key: Span` and `produce(&mut self,key) -> oneshot::Receiver<Bytes>`. Its clone should clone an attachment request handle, not the non-Clone Archive. Existing `Consumer` receives `Delivery { key, subscribers }` plus `Bytes` and returns a disposition receiver. Generic Engine uses the same key for both and adds `Subscriber: Ord` to the trait's Clone/Eq/Send bound. Reuse the existing resolver mailbox as the fetch handle. [Producer](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/resolver/src/p2p/mod.rs#L103), [Consumer](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/resolver/src/lib.rs#L146), [Engine bounds](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/resolver/src/p2p/engine.rs#L93).

The narrow adapter flow is: Producer admits a serving request -> existing archive owner performs `get` -> encode the selected, key-valid record into bounded response bytes -> return through the oneshot. Closing the producer response becomes a resolver error response; the resolver already handles peer request IDs/retry. Consumer validates bytes against the **peer-visible key**, then hands them to the same retained storage/custody owner and correlates local native-context subscribers. No second fetch engine is needed. [Request serving](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/resolver/src/p2p/engine.rs#L360).

Consumer's `Complete`, `Ambiguous`, `Invalid`, `Ignored` have different transport effects. Subscribers are local observations, not the peer's validity contract. A same-key valid record that does not satisfy every subscriber can be ambiguous; canceled wants can be ignored. A storage error must not be mapped to bool false/Invalid and penalize a peer. Custody failure remains local application failure, and pending archive ownership must survive cancellation where required. Do not equate transport Complete with Automaton's durable custody verdict. [Outcome semantics](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/resolver/src/lib.rs#L114).

**Concrete admission point:** Engine's outstanding `serves` pool is explicitly unbounded and its source assigns limiting concurrent remote serving requests to Producer (which may drop requests). A bounded request mailbox by itself does not bound spawned outstanding reads, accumulated serve futures or bytes. Reuse a bounded admission/ownership mechanism under the attachment, with the limit/policy unspecified. Whole-response sizing includes resolver ID/tag/Bytes framing as already documented; limiting only the archive value is insufficient. [Unbounded serve futures](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/resolver/src/p2p/engine.rs#L77), [wire size](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/resolver/src/p2p/wire.rs#L28), [payload framing](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/resolver/src/p2p/wire.rs#L109).

| Alto validator | Engine opens immutable finalized-certificate/block archives and moves both into `MarshalActor::init`; Actor owns the stores; buffer is a distinct Engine/Mailbox | Demonstrates one store owner serving borrowed queries while mutations consume/recover its own handles; global finalized height schema is not producer-lane custody |

Native public `marshal::store::Blocks` already has direct implementations over both archive variants. Its block bound is the existing consensus `Block` (height, codec, digest, Send/Sync), and put derives a global finalized height/digest. It is a storage contract, not a ready-made pre-cut Multimmit body owner. No need to invent a replacement generic block database; use Archive directly with the chosen native/application schema where the finalized-only Blocks contract differs. [Blocks contract](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/consensus/src/marshal/store.rs#L118), [existing immutable implementation](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/consensus/src/marshal/store.rs#L285), [existing prunable implementation](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/consensus/src/marshal/store.rs#L389), [Block bound](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/consensus/src/lib.rs#L62).

Native Marshal's full-commitment query validates the stored commitment after digest lookup, which is a concrete precedent for a digest hit requiring a stronger identity check. Tempo's private `get_header` checks hot archive then execution headers and its startup verifies header number/hash against the certificate. Neither provides generic authenticated Multimmit header/context/parent lookup. Tempo's header-by-hash path also has a different finalized restriction from header-by-height; it is not evidence that every returned header is finalized. [Native full-commitment check](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/consensus/src/marshal/core/actor.rs#L2149), [Tempo header verification](https://github.com/tempoxyz/tempo/blob/61c979a524f9af5de9c540a0088c429a44741e4c/crates/consensus/src/alias.rs#L316).

## 4. Recommended small reader-page changes

Preserve current pages/headings, the five public traits, blank policy decisions, and diagrams. No new declaration or default is needed.

1. **block-body existing primitive table:** split the general Archive row into immutable/ordinary index+key behavior, prunable MultiArchive's `put_multi/get_all/has_at`, and covering sync. Say `has_at` is exact index/key presence, not custody. Explain first-value index lookup and same-key ambiguity in the existing open-schema paragraph.
2. **block-body ownership paragraph:** add one sentence that async `get(&self,...)` is already public, concrete archives are not Clone read handles, and Producer clones an attachment request handle to the existing owner. This makes the implementation recipe concrete without adding an actor.
3. **block-body resolver paragraph:** state the actual unbounded `serves` pool and Producer admission responsibility. Existing policy cells remain empty; no numeric budget, priority or drop policy is adopted.
4. **integration body assembly item 4 / constructor table:** name Archive `Identifier::Key/Index` and optional prunable `MultiArchive::has_at`, with native header-ID -> commitment/context binding. Keep using the public generic resolver and record that actual-chain private stores/wrappers are ownership patterns, not exported Baton-ready APIs.
5. Optional compact note under existing storage ownership prose: immutable sync owns Freezer checkpoint/Ordinal metadata recovery, so a body adapter need not implement another recovery map. Avoid exposing raw Cursor as authenticated protocol identity or prescribing Freezer as the body backend.

No confirmed protocol bug, completed custody proof, native direction-preservation proof, full-body ACK barrier, selected archive layout, backend, quota, retention number, or additional public application contract follows from this audit. This is source-grounded reuse guidance and a documentation delta only.
