**The recipe is sound within its stated boundaries. Two small verifier clarifications should accompany reader-page publication:** batch verification does not replace the full sharing material needed for threshold-share verification; certificate-only constructor checks do not authenticate the provenance or thresholds of supplied group identities. The remaining recommendations correctly reuse public machinery and preserve the application bridges.

## Verifier material and contextual limits

`multimmit::scheme::bls12381_threshold::{Roster, Scheme}` are public through `multimmit::scheme`. `Scheme::certificate_verifier` takes Config, a PoP-verified Roster, and complete DA/nullification public identities. It stores `da: None` and `nullification: None`. `verify_vqc` and `verify_lqc` verify the expected epoch, structural/codec validity, reconstructed aggregate transcript and signatures, returning CertificateId. They do not evaluate application policy, exact history/parent linkage, the owner's selected sticky finality source, dense order or body custody. The report explicitly preserves these limits.

The table's phrase “full verifier or batch verify_artifacts when raw shares are required” should become **“use a full verifier with the threshold sharings for raw shares; optionally call its batch verify_artifacts.”** `artifact_claims` for DaVote uses `self.da.as_ref()?`; Nullify uses `self.nullification.as_ref()?`. A certificate-only verifier calling the batch method still lacks those sharings and returns invalid verdicts for those share artifacts. No batching API elevates its key-material role. Verified in scheme/bls12381_threshold.rs lines 293–326 and 946–981.

Also retain an explicit trusted epoch-key provenance requirement. `Roster::verify` checks ordinary identity/key uniqueness and proofs of possession; it does not authenticate the network's committee assignment on its own. `validate_certificate_material` only checks expected participant count and nonzero, distinct group identities. Unlike a full verifier, certificate-only construction has no public sharing polynomial with which to validate the sharing threshold. Trusted epoch configuration/key-generation history must supply the correct group identities. Even full constructors cannot prove independent generation of DA and nullification sharings, as the type security contract states. This sharpens the report's “existing verified roster/config path” wording without introducing a new key scheme or changing thresholds. Verified in scheme/bls12381_threshold.rs lines 110–158, 182–190 and 1354–1370.

## Tally opening preserves unsigned-body provenance

Public `types` re-exports `history::*` and `tally::*`; the machinery here is application-callable. `Tally::vote<V,H>` reconstructs a `VoteBody<D>` using a supplied exact LeaderBlock, eligible signer and CodecConfig. It checks dimensions and signer membership and creates the body with `VoteBody::for_leader`. `ConflictingVote::vote_body` reconstructs its body using the aggregate's Round and config. Neither produces an individual signature, and tally reconstruction alone is not aggregate verification. The report correctly requires retention of the original aggregate certificate and row provenance and does not present reconstructed bodies as raw Vote artifacts.

A valid aggregate can authenticate its rows while native selected-source provenance and application interpretation remain separate. The report's prohibition on replacing an owner-selected sticky pool by an arbitrary n−f subset is consistent with private `pool_evidence`, which hashes selected per-identity body evidence rather than every original signature. `FinalTips::from_pool` remains pub(crate), and its algebra module remains private. Public tally access does not solve this extraction/export boundary.

## Public codecs versus Artifact

`ViewProof` is re-exported from the private machine module at multimmit/mod.rs lines 242–246. Its Read/Write/EncodeSize implementations exist, with bounded `CodecConfig` for reading. `TipRecord` is public through `types`; its Read config is the exact chain count and its constructor validates nonempty, canonically indexed tips. Its commitment is domain-separated over parent and encoded tips. The report correctly distinguishes these codec/shape checks from proof-backed safe-tip derivation and exact history validation.

`Artifact` is also re-exported but has no Read or Write implementation in the inspected native files. Its variant-dependent `encoded_len` and `id` methods do not implement a Codec for the union. Archive requires `Value: Codec + Send`. Consequently, `Archive<Artifact>` is not justified, while `ViewProof` or an application Codec envelope over existing public variant codecs is a legitimate source-based candidate. The native network Envelope unions live under private actors, so a private wire union cannot be assumed to be an external import either. The report does not do so. Envelope/tag/index design remains open, including bounded decode and exact identity checks.

## Same-view records and archive semantics

Archive::put is a documented no-op at an occupied index; indexing only by view would lose subsequent same-view witnesses/source revisions. MultiArchive::put_multi allows multiple entries at that index, get_all retrieves them, and has_at checks the exact index/key association. Reusing that trait or adopting unique export ordinals is appropriate. No particular archive implementation or ordinal schema is selected by the report.

Reader prose should retain three ordinary archive caveats already compatible with this recipe: get by index on a MultiArchive returns the first item; a repeated key at multiple indices may resolve to any associated value; puts below a prune floor may succeed without storing anything. Therefore retained evidence identity/source revision and exact presence remain application obligations. Archive gap indices are local storage holes, never proof of a nullified or settled-empty protocol slot. Sync covers the writes captured at its boundary; later accepted records need covering sync too. Mutation consumes the archive handle and requires cancellation-safe ownership, just like the existing body storage attachment.

## Journal / Metadata durability and QMDB linkage

The public variable contiguous Journal exists, and Contiguous::read/replay plus Mutable::append/commit/sync are production traits. Replay is bounded by journal bounds and the selected byte budget. Appending supplies a journal position, not the application emitted cursor or a durable acknowledgement. Mutable::commit durably persists but may require recovery; sync additionally guarantees no startup recovery. Its start_sync handle covers current state and later appends need separate coverage. None derives terminal native interpretation or prevents an application from recording a wrong predecessor.

Metadata is publicly re-exported. Its documented dual-blob/version/checksum mechanism atomically commits the small local metadata collection. `put` changes memory and requires sync; put_sync commits all pending metadata changes. This local atomicity is not an atomic transaction with the contiguous journal, retained archive, QMDB state, execution outputs or direct/imported provenance. The report explicitly preserves that distinction and correctly keeps crash ordering and linkage with the application contract.

`Orderer::acknowledge` must validate the exact recoverably durable CommitResult before advancing its acknowledgement record; losing that metadata update can lead to idempotent redelivery rather than undoing emitted choices. Native Reporter notices, bounded inspection and a covering Running::serve proof do not substitute for the durable exact-source handoff. The report keeps those semantics and does not make Executor's delivery ACK a native voting/cut barrier.

## Publication recommendation

Carry the two verifier clarifications into any new reader-facing public-call table. Preserve the current open source-export/extraction facade, codec/index/retention choices and application crash-linkage obligations. With those qualifications, the proposed Scheme/Tally/public typed records → archive/generic resolver → narrow native bridge → contiguous delivery → Journal/Metadata assembly is a defensible primitive-reuse direction. It establishes source availability and fit, not a selected concrete type assembly, compiler compatibility, integration execution, exact-prefix preservation proof or completion of the six-hour goal.
