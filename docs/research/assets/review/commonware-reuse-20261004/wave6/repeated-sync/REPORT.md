# Wave 6: repeatable validator state sync with native QMDB primitives

## Finding and scope

Baton can reuse the **existing public QMDB sync entrypoint and P2P Source service** for repeated selected certified targets. It need not copy the one-time Stateful bootstrap actor or introduce another operation-fetch/proof-verification engine. The missing work is the application handoff: bind a selected execution certificate to the storage target and outputs, own a candidate database without interfering with direct execution, verify the completed material, then switch under the existing canonical writer/fencing/recovery contract.

This is a fresh pinned source/API audit, not a compiled assembly or protocol safety proof. Actual graph remains `commonwarexyz/monorepo@534af0ede48affd35b2111522527547b4cc9bf72`; release `v2026.9.0` MCP responses corroborate APIs only. No backend, root definition, schema, codec, target-selection, channel sizing, sealing or session policy is selected. Five public Baton traits and their signatures stay unchanged.

The [source manifest](source-manifest.json) records 35 independently fetched files, complete fresh tree receipts, SHA-256 and matching Git blob identities. All succeeded. Native sources, Constantinople and Alto were checked directly; indexed release responses are retained separately.

## Exact public entrypoints and ownership

The usable entrypoint is `commonware_storage::qmdb::sync::sync`, rather than the crate-private `Engine` or `step`/`apply_operations` methods:

```rust
pub async fn sync<DB, S>(
    config: Config<DB, S>,
) -> Result<DB, Error<DB::Family, S::Error, DB::Digest>>
where
    DB: Database,
    DB::Op: Encode,
    S: SourceFor<DB>;
```

`SourceFor<DB>` means `Source<Family = DB::Family, Op = DB::Op, Digest = DB::Digest> + 'static`; source cloning is not required. Public Any and Current variants implement `sync::Database` with their existing native operation/journal/config types. Current additionally needs its actual `Graftable` family, chunk parameter and variant bounds. The native Any/Current implementation macros record all ordered/unordered and fixed/variable bounds; this report does not fix one variant. [Entrypoint and SourceFor](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/storage/src/qmdb/sync/mod.rs#L41), [public database contract](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/storage/src/qmdb/sync/database.rs#L48), [Any implementation](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/storage/src/qmdb/any/sync/mod.rs#L125), [Current implementation](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/storage/src/qmdb/current/sync/mod.rs#L234).

The public `sync::engine::Config<DB,S>` fields are exactly:

| Field | Assembly meaning |
|---|---|
| `context: DB::Context`, `db_config: DB::Config` | Create/open the native journal and reconstruct a database; **no existing live DB argument** |
| `source: S`, `target: Target<DB::Family,DB::Digest>` | Existing operation/proof service and caller-authenticated target |
| `max_outstanding_requests: usize`, `fetch_batch_size: NonZeroU64`, `apply_batch_size: NonZeroU64` | Existing fetch/apply controls; values remain open |
| `update_rx: Option<mpsc::Receiver<Target<...>>>` | Strictly advancing selected targets during this session |
| `finish_rx: Option<mpsc::Receiver<()>>` | Requests return after the current target is reached; `None` returns upon reaching it |
| `reached_target_tx: Option<mpsc::Sender<Target<...>>>` | Progress notification, with awaited channel backpressure |
| `max_retained_roots: usize` | Retain prior target roots for in-flight proof verification; not application result/certificate storage |

Native imports use `commonware_utils::channel::mpsc`, not an interchangeable independently versioned channel type. The actual constructor input table is [Config L99–142](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/storage/src/qmdb/sync/engine.rs#L99). `sync::Database::from_sync_result` and `persist_sync_result` are existing database implementation hooks, not a proposed new Storage interface.

The existing `commonware_glue::stateful::db::StateSyncDb::sync_db(context, config, source, target, tip_updates, finish, reached_target, sync_config) -> Future<Result<Self, Self::SyncError>>` is also public and implemented for Any/Current variants. It delegates to the same engine. Its `ManagedDb` bound is a storage wrapper bound; using it does not require implementing `stateful::Application`. The helper `sync_standard_db` is crate-private, so external code calls the public trait or `sync::sync`. `StateSyncSet::sync` explicitly documents one-time initialization and returns a block `Anchor`; it does not establish a repeated execution-certificate handoff. [StateSyncDb](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/glue/src/stateful/db/mod.rs#L611), [delegate](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/glue/src/stateful/db/mod.rs#L1663), [one-time set](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/glue/src/stateful/db/mod.rs#L699).

## Four objects must stay distinct

1. **Execution statement/certificate**: the adopted exact input/range, canonical base, order, runtime, result and eligible f+1 signatures. QMDB does not parse or authenticate this application statement. DirectExecuted versus ImportedVerified remains separate provenance.
2. **Storage target**: `Target<F,D> { root: D, range: NonEmptyRange<Location<F>> }`, where root is the **operations root** and range is retained storage-log coordinates. It is not the transaction/block execution range.
3. **Authenticated fetched material**: `Response::Operations { proof, operations }` or `Response::Boundary { proof, op, pinned_nodes }`. These prove native operation bytes at requested locations under the target's operations commitment, not the full execution statement or associated application outputs.
4. **Completed candidate DB / locally prepared batch**: a reconstructed native DB returned from `sync`, or a locally built sealed batch at the exact applicable base. Neither is the peer's f+1 certificate.

For Current, `Db::root()` is canonical while `sync::Database::root()` deliberately returns the ops root. A sender can call `Db::ops_root_witness() -> Result<OpsRootWitness<F,H::Digest>, Error<F>>`; the receiver can call `witness.verify::<H>(&ops_root, &trusted_canonical_root) -> bool`. This uses existing codec and root-combination material, but the sync engine does not perform that witness check. After reconstruction Storage must compare the actual canonical/result commitment as required by the chosen execution statement as well. Multiple DBs or additional output commitments need their own exact statement binding; a witness for one Current DB does not certify an application-wide tuple. [Target](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/storage/src/qmdb/sync/target.rs#L16), [response types](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/storage/src/qmdb/sync/source.rs#L226), [Current root distinction](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/storage/src/qmdb/current/sync/mod.rs#L6), [witness](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/storage/src/qmdb/current/proof/mod.rs#L57), [sender API](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/storage/src/qmdb/current/db.rs#L292).

`Target::advances` checks only valid increasing end and nondecreasing start, assuming the same append-only QMDB. It does not authenticate consistency, branches or execution context. Current `range.start` must be at or below `Db::sync_boundary()` and retained; values above it can prevent grafted reconstruction. A certificate's next execution interval cannot simply become this lower storage bound. [advances](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/storage/src/qmdb/sync/target.rs#L29), [safe Current boundary](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/storage/src/qmdb/current/db.rs#L431).

## Repeated sessions: existing engine, application handoff

A minimal source-compatible shape is repeated invocations of public `sync::sync` for selected certified targets, using the existing Source mailbox and actual database configuration. Optional updates can instead advance the target within one invocation. These are alternatives, not an adopted session policy; a permanently running updating session does **not** return a usable DB for every reached target.

The decisive distinction is **progress versus handoff**. `is_ready_to_complete` checks journal size and pinned-node availability; `step` calls `report_reached_target` before `complete`. Only `complete` syncs the journal, reconstructs the DB, checks its operations root and invokes variant persistence. Thus `reached_target_tx` must not stop direct execution, authorize imported signing, publish a usable database or cause durable delivery ACK. The returned DB still needs application result/output verification and recoverable canonical linkage. With updates, `sync` returns only DB, so the adapter must retain and reconcile the final selected certificate/target identity; receiving an old reached-target message is insufficient. [readiness](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/storage/src/qmdb/sync/engine.rs#L522), [notification/return order](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/storage/src/qmdb/sync/engine.rs#L724), [rebuild/check/persist](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/storage/src/qmdb/sync/engine.rs#L777).

The candidate's partitions and handle ownership cannot silently alias a live database. `Journal::new` reuses on-disk data within the target and may prune, rewind or clear outside it; engine reset also resizes the journal. These are real storage mutations. An independently owned candidate store is one possible way to keep direct work running until verification; exclusive same-store handoff is another but needs a fence before any shared storage mutation and cannot be presented as concurrent preparation. No staging partition or switching policy is chosen here. Opening two native handles on the same partitions is not justified by the fact they have different Rust owners. [journal mutation contract](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/storage/src/qmdb/sync/journal.rs#L23), [fixed reopen/prune/rewind](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/storage/src/qmdb/sync/journal.rs#L113), [target resize](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/storage/src/qmdb/sync/engine.rs#L383).

Existing engine responses are validated against requested proof size, response shape and operation limits, then range inclusion/pinned nodes before appending; operations stream contiguously. A resumed store reuses persisted journal data and attempts local pinned-node recovery, then final root verification. This is useful native recovery, not Baton recovery of certificate, exact order, outputs, cursor, writer generation and ImportedVerified provenance. Any/Current reconstruction may persist state before returning; variant `persist_sync_result` is `Ok(self)`, not a transaction spanning application metadata. Failed/cancelled candidate storage remains subject to native reopen/recovery rules; do not reinterpret an interrupted local session as a verified completed import. [proof checks](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/storage/src/qmdb/sync/engine.rs#L577), [native resume](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/storage/src/qmdb/sync/engine.rs#L245), [Current persisted reconstruction](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/storage/src/qmdb/current/sync/mod.rs#L225).

After applicable material is verified, the existing Executor/Storage contract must recheck exact local base/order/runtime and selected target, revoke conflicting worker/batch access across clones, promote under the shared canonical writer, and recoverably link imported provenance/state/outputs/cursor before ACK. `Shared::write` / `WriteSlot::put` provides a by-value cell mutation seam, not that protocol: dropping an empty slot loses the handle, and old cloned batches retain shared access until fenced. Neither `Shared` replacement nor `attach_database` is crash-atomic switching. Existing `Db::apply_batch` does not promise durability without commit/sync or its sync handle. [write-slot semantics](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/glue/src/stateful/db/mod.rs#L157), [Any apply durability](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/storage/src/qmdb/any/batch.rs#L2743), [Current commit/sync](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/storage/src/qmdb/current/db.rs#L721).

## Existing peer service can survive multiple sync sessions

`commonware_glue::stateful::db::p2p::Actor::new(context, Config<P,D,B,DB>) -> (Self, Mailbox<...>)` and `Actor::start(self, (Sender, Receiver)) -> Handle<()>` are public. `Mailbox` is Clone and implements QMDB `Source`; the actor already coalesces identical requests and routes validation feedback through the resolver. Native bounds include `Shared<DB>: Source<Family=F>` and **`Op<DB>: Codec<Cfg=()> + Send + Clone + 'static`**. This existing P2P wrapper does not automatically fit a chosen operation codec with non-unit read config. Keep one native dependency graph and adapt only an actual codec boundary if necessary. [Actor constructor/bounds](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/glue/src/stateful/db/p2p/actor.rs#L112), [start](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/glue/src/stateful/db/p2p/actor.rs#L145), [Mailbox Source](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/glue/src/stateful/db/p2p/mailbox.rs#L129).

`Mailbox::attach_database(&self, Shared<DB>) -> ()` can attach again, and the actor explicitly replaces its serving handle. It enqueues a message without a readiness ACK and does not detach, fence old holders or persist the application's canonical switch. Its serving Request carries size/start/max_ops, not execution certificate context or the root; response validation supplies root binding. Retain certificate/context alongside the reused native transport rather than adding these fields to an upstream Request by assumption. Native serving also requires retained historical operations/pinned nodes; a result certificate alone does not guarantee peer material availability. [reattach](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/glue/src/stateful/db/p2p/actor.rs#L228), [attach enqueue](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/glue/src/stateful/db/p2p/mailbox.rs#L123), [request fields](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/storage/src/qmdb/sync/source.rs#L27).

## Direct delta reuse: material yes, arbitrary batch import no

Any `historical_proof(historical_size, start_loc, max_ops)` and Current `ops_historical_proof(...)` return `(merkle::Proof<F,H::Digest>, Vec<Operation<F,U>>)`. `pinned_nodes_at` and native `Source::serve`/Response codecs already cover corresponding material transport. Current also has grafted `range_proof` for active-operation proof semantics; it must not be substituted for ops-tree sync proofs. [Any material](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/storage/src/qmdb/any/db.rs#L501), [Current material](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/storage/src/qmdb/current/db.rs#L410).

A peer native operations suffix can therefore reuse existing material/proof types and the native sync reconstruction, provided its trusted target, complete safe storage range and local retained/reopened data fit. The suffix alone is not a public in-place `apply_operations` method: that engine method is crate-private, and public `Db::apply_batch` accepts a locally prepared `Arc<MerkleizedBatch<...>>`. Native batch diff/journal/bounds fields are private and no peer-wire batch constructor/codec was found in the inspected Any/Current batch modules. Do not serialize a local Shared batch or treat a `Response` as a prepared batch.

An application change-set path can reuse existing `new_batch/write/merkleize/validate_batch/apply_batch` at the exact live base instead. Its application codec/materialization must preserve the actual native operation/root semantics and full result/output binding; replaying only final key/value mutations can generate different operation history, compaction/floor or roots from the peer. `validate_batch` checks local applicability, not execution-certificate validity or arbitrary raw wire operations. These are two distinct reuse paths and neither fixes the wire schema. [native batch fields](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/storage/src/qmdb/any/batch.rs#L338), [local validation/apply](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/storage/src/qmdb/any/batch.rs#L2733), [operation codec/kinds](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/storage/src/qmdb/any/operation/mod.rs#L23).

## Actual chain composition and release corroboration
