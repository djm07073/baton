# Final challenge: can an existing App-only hook enforce the protected prefix?

Fresh source counterexample search at native `6233438985d8249d2b2bc1204191d5d405652288`, 2026-10-09. No native/docs changes or tests. No overlooked existing attachment was found that establishes the requested general canonical protected-prefix guarantee while preserving ordinary native construction/validation and the no-wait cut requirement.

| Attempted existing seam | Actual boundary and reason it does not supply that guarantee |
|---|---|
| `ProposalPolicy` | `propose_chain` chooses a certified anchor and sets an optional contiguous local DA-voted suffix budget to pipeline depth or zero (`machine/vote_body.rs:119–160`). It does not accept a cross-lane comparator/prefix; both Endorsed and Certified use the same native validation rules. This existing policy is sufficient for that local construction choice only. |
| `LeaderSchedule::from_fn/from_order` | The function is evaluated while materializing a fixed committee-period rotation; subsequent leaders are indexed from the immutable array (`config/protocol.rs:16–73,113`). It chooses the participant, not a live report window, actual proposal parent, payload ordering or adoption rule. A stateful callback captured during construction is not retained as a per-cut hook. |
| `Automaton` | The callback receives producer Context and a body digest; certificates and leader blocks do not reach it (`multimmit/mod.rs:50–64`). A Baton message could be encoded in an opaque application body, but the native leader/vote logic has no branch that interprets it as a frozen cross-lane policy. Delaying valid-body custody to steer availability neither authenticates adoption nor preserves the required no-wait/progress behavior. |
| `Inspector`, Reporter, Relay | Inspector exposes diagnostics; native Reporter observes already processed activity; Relay requests body dissemination. None returns a replacement proposal or validation verdict for a leader cut (`engine/mod.rs:74–111,176–184`; shared traits in lib.rs). Diagnostic knowledge of a view/frontier does not grant an atomic adoption/signing hook. |
| Marshal `LqcVerifier` | Its public method returns only `Result<(), Error>` for a peer-resolved L-QC or supplied floor anchor (`marshal/types.rs:42–52`; backfill/actor.rs:489–514; synchronizer/floor.rs:93–98). Most decisively, a native `ProtocolAccepted(Artifact::Lqc)` goes through catalog.stage_lqc → synchronizer.trigger without this hook (`service/router.rs:249–265`). A custom verifier can reject external material; it cannot become a universal pre-vote Baton validator or change Marshal traversal. Rejecting local delivery would not undo native finality. |
| Public `LeaderBlock::new` / signing helpers | LeaderBlock exposes a constructor for existing round/parent/history/per-chain proposals (`types/block.rs:802–825`), not a submission hook into Engine. Production signing helpers are crate-private; they become public under mocks (`scheme/bls12381_threshold/mod.rs:24–38`, sign.rs:51–62). Constructing a value or using a test-only signer does not replace the native proposal path. |

The actual path seals the proposal privately: choose the scheduled leader and valid parent, collect `chain.propose_chain(tip)` per lane, then construct LeaderBlock and issue its signing request (`machine/view/proposal.rs:190–216,285–354`). Signature verification authenticates the scheduled leader and embedded certificates (`scheme/bls12381_threshold/claims.rs:168–182,262–287`); voting additionally checks parent/history/anchor extension (`view/proposal.rs:426–486`). No stage receives the App's selected Baton prefix/window/rule.

Marshal then derives FinalTips from the L-QC and traverses pass A followed by pass B, offset-major in chain order (`marshal/protocol/order.rs:258–266,333–339,444–461,487–546`). Concrete counterexample: when A1 and B1 both occupy the first pass above the same frontier and A precedes B in chain order, the stream yields A1 then B1. An App-selected B1→A1 prefix does not alter that traversal through any of the seams above. Waiting to release/reordering Updates changes App behavior after native order; it does not establish a canonical prefix accepted by the protocol.

The limit is specific: ordinary native body/order machinery remains reusable, and an App-only scheduler can guide speculation. A chosen prefix that happens to match native order needs no special mechanism for that particular result. The unresolved requirement is authenticated general policy adoption with preserved leading order across extension/recovery. It needs native integration and consistent Marshal interpretation, as current docs say. This inspection establishes the present API/control-flow gap; it is not a proof of a future extension's safety or liveness.
