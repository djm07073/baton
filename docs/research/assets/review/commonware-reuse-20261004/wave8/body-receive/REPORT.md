**Existing buffered subscription already performs local cache-hit-or-wait delivery.** Connect that handle and the generic resolver Consumer to the existing custody owner; there is no need for a new generic incoming-body stream, polling cache, duplicate message store or automatic forwarding actor. ## Startup → raw receive → body handle

Public `buffered::Engine::new(context, Config<P,M::Cfg,D>)` returns the Engine and cloneable Mailbox. Start the Engine with the raw registered `(Sender<PublicKey=P>, Receiver<PublicKey=P>)` pair; it calls the existing codec `wrap` using the selected body config and subscribes to its Provider. No additional typed/background receiver belongs before this engine. WrappedReceiver decodes the complete frame and retains the authenticated transport peer separately; decoding errors are returned to this loop and logged/dropped. The buffer itself does not call the application's body validity/custody logic or peer Blocker for codec failure. [Construction and start](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/broadcast/src/buffered/engine.rs#L122), [Complete-frame receiving](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/p2p/src/utils/codec.rs#L111), [Actual incoming arm](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/broadcast/src/buffered/engine.rs#L207).

After a successful decode, the Engine computes `M::digest()`, wakes existing digest waiters, and records a resident cache entry if the sending peer is in `latest.primary`. Per-peer digest deques and global digest reference counts share one cached Arc across peers. A duplicate from the same peer moves its deque entry forward; a different peer adds a reference without a second stored body. Eviction removes the body only after its last resident deque reference disappears. There is no receive-triggered rebroadcast: sending runs only through the explicit Broadcast mailbox path. These are body-cache identities, not authenticated native header IDs or canonical execution membership. [Receive/hash and waiter delivery](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/broadcast/src/buffered/engine.rs#L279), [Dedup/residency](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/broadcast/src/buffered/engine.rs#L330), [Explicit send](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/broadcast/src/buffered/engine.rs#L236), [Eviction](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/broadcast/src/buffered/engine.rs#L367).

Residency is narrower than delivery: waiters are notified **before** the latest-primary eligibility check. A body can therefore satisfy an existing subscription without being kept for a later get. Primary membership is transport/cache eligibility, not the body author's membership, an execution-signing committee or proof of durable custody. Engine construction begins with an empty cache/primary snapshot, and Provider updates drive residency. Do not add a peer readiness round or assume get(None) proves the bytes never arrived. [Wait-before-residency](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/broadcast/src/buffered/engine.rs#L296), [Peer update/eviction](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/broadcast/src/buffered/engine.rs#L379).

## Existing handles close the local acquisition path

Public `Mailbox::subscribe(&self, digest) -> oneshot::Receiver<Arc<M>>` asks the existing Engine to either return its cached Arc immediately or retain a waiter for later local/network delivery. This avoids another application polling loop and the lookup-then-register gap. The returned Arc keeps that object's material alive after cache eviction; it does not establish archive durability. The public mailbox has get/subscribe/broadcast_shared, not an all-incoming stream, archive promotion callback or cache-only insertion API. Unsolicited bodies may remain transient until an exact request/header needs them. [Public mailbox](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/broadcast/src/buffered/ingress.rs#L99), [Cache-hit-or-wait](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/broadcast/src/buffered/engine.rs#L251).

Dropping the receiver cancels the waiter; the Engine cleans closed responders. get returns None on both a cache miss and Engine shutdown. Subscriptions do not initiate peer fetch, and cached/decoded bodies are not application-valid or durable just because those handles return. Keep the existing task lifetime and exact header/context/required-parent/custody checks. Ready mailbox capacity, per-peer resident count and total body bytes/waiters/overflow are different bounds; all concrete limits remain open. [Cancellation/cleanup](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/broadcast/src/buffered/engine.rs#L396), [Shutdown behavior](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/broadcast/src/buffered/ingress.rs#L99).

Generic resolver response acquisition stays a separate existing path. The Engine correlates response id and peer to an active requested key, then sends Delivery{key, subscribers} + Bytes to Consumer without blocking its loop on validation. It coalesces existing fetch keys and maintains subscribers internally. It does **not** insert a resolved body into the broadcast cache automatically. Consumer can hand verified expected bytes directly to the same custody owner; rebroadcasting merely to inject the buffer would be an additional publication decision, not a necessary storage step. [Response dispatch](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/resolver/src/p2p/engine.rs#L405), [Fetch coalescing](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/resolver/src/p2p/engine.rs#L235), [Consumer contract](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/resolver/src/lib.rs#L149).

Consumer outcomes retain their exact meaning: Complete clears delivered subscribers and may locally redeliver the accepted response to later subscribers; Ambiguous retries a wire-valid response needing different evidence; Invalid blocks/retries an initially invalid peer response; Ignored retires the whole key without retry. Stale local context and local archive failure must not become peer-invalid data. The current body page already states those distinctions, serving limits and subscriber/custody lifetime split; no new retry service or outcome policy is proposed. [Delivery handling](https://github.com/commonwarexyz/monorepo/blob/534af0ede48affd35b2111522527547b4cc9bf72/resolver/src/p2p/engine.rs#L426).

## Actual Tempo and Alto reception

Tempo builds the buffer once, starts it on the body channel, and passes its mailbox into Standard Marshal. Its Marshaled wrapper chooses Inline or Deferred, both delegating through that Marshal. Alto does the same and starts body handling before consensus. These graphs demonstrate composition, not a public native Multimmit body receiver or a requirement to adopt Simplex Block/Application. [Tempo construction/start](https://github.com/tempoxyz/tempo/blob/61c979a524f9af5de9c540a0088c429a44741e4c/crates/consensus/src/consensus/engine.rs#L207), [Tempo Marshal handles](https://github.com/tempoxyz/tempo/blob/61c979a524f9af5de9c540a0088c429a44741e4c/crates/consensus/src/consensus/engine.rs#L526), [Alto startup](https://github.com/commonwarexyz/alto/blob/1d87569348b5560699465a72d691d90f18affb9c/chain/src/engine.rs#L462).

Standard's Buffer implementation directly forwards digest/commitment subscriptions to buffered Mailbox. Marshal checks local buffer/storage, then its private Subscriptions owner registers the underlying buffer waiter and applies caller-specific resolver fallback. Inline/Deferred register local candidate waits before publishing their verification gates; the inspected Simplex candidate wait may deliberately be local-only while its certification path starts recovery. Do not copy that certification-dependent waiting policy into native Automaton: native full-body lookup/fetch remains the existing separate adapter requirement. No additional Ready/ACK gate follows. [Public buffer implementation](https://github.com/commonwarexyz/monorepo/blob/d476a2361ce6840d2b9d0aa6fb30a924429046d4/consensus/src/marshal/standard/variant.rs#L90), [Actual local lookup/fallback](https://github.com/commonwarexyz/monorepo/blob/d476a2361ce6840d2b9d0aa6fb30a924429046d4/consensus/src/marshal/core/actor.rs#L1081), [Private waiter owner](https://github.com/commonwarexyz/monorepo/blob/d476a2361ce6840d2b9d0aa6fb30a924429046d4/consensus/src/marshal/core/subscriptions.rs#L93), [Simplex wait-before-gate](https://github.com/commonwarexyz/monorepo/blob/d476a2361ce6840d2b9d0aa6fb30a924429046d4/consensus/src/marshal/standard/inline.rs#L430).

Those private helpers are not an externally importable generic subscription framework. The specialized resolver Handler's receive methods are also crate-private. The public buffer mailbox and generic resolver callbacks are sufficient for native acquisition, with application correlation/custody retained under the existing owner. Even Marshal's validated-block subscriptions explicitly notify before persistence and promise no durability; its later finalized dispatch is a different contract. [Private resolver bridge](https://github.com/commonwarexyz/monorepo/blob/d476a2361ce6840d2b9d0aa6fb30a924429046d4/consensus/src/marshal/resolver/handler.rs#L131), [Subscriptions versus durability](https://github.com/commonwarexyz/monorepo/blob/d476a2361ce6840d2b9d0aa6fb30a924429046d4/consensus/src/marshal/core/actor.rs#L1254).
