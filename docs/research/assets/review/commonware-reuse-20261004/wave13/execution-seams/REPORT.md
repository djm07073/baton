## Precise ownership issue

`overview/interfaces.md:29` equates Executor, Orderer, TxPool and optional Baton CommitResult types. Actual central Rust declarations receive CommitResult by value: TxPool::on_commit (`rust-interfaces.md:72–74`), Orderer::acknowledge (`:139–141`) and Baton::on_commit (`:203`). Executor/Storage CommitResult is only Send (`:227,300`), not the explicitly Clone PreparedResult (`:226,298`). Type equality and Send do not create another owned value for the next receiver.

This is **not a diagnosed compiled generic bug**. A concrete associated type may already implement Clone, carry a shared immutable receipt, or be reconstructed from retained exact durable evidence. The trait intentionally leaves that choice open. The current generic-type paragraph, however, only explains matching types and context validation; unlike PreparedResult, it does not spell out the ownership needed by the displayed multi-receiver route. Naming that requirement makes actual assembly clearer without changing the public bound or prescribing storage layout/actor policy.

The proposed paragraph after the associated-type table is:

> `CommitResult` is passed by value: use concrete cloneable receipt handles or recover copies of the same immutable receipt for multiple consumers; type equality and `Send` do not duplicate an owned value.

This does not make callbacks atomically processed, make pool readiness equal to local enqueue, add Baton approval, or require another receipt store. Existing durable CommitResult identity, backend processing/replay and exact Orderer recovery contracts continue to govern each receiver. Upstream Reporters/Exact are not asserted to provide async application fanout or durable receipt duplication automatically.
